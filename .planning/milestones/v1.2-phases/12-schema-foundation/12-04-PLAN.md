    - .planning/phases/12-schema-foundation/12-RESEARCH.md (Pitfall 1 — symptom of misregistration is exactly the failure mode this UAT catches)
  </read_first>
  <what-built>
    Plan 03 also registered `db.on('versionchange', () => window.location.reload())` at module-top-level in `src/db/database.ts`. This handler fires on tab A when tab B opens a connection requesting a higher database version (because tab B loaded a newer bundle). The handler causes tab A to reload itself, releasing its IndexedDB connection so tab B's upgrade can proceed.

    Without this handler, Dexie's built-in default would close tab A's connection and `console.warn()` — but the React tree in tab A still holds references to query results via `useLiveQuery`, which causes the white-screen crash that SCHEMA-02 targets.
  </what-built>
  <action>
    The developer (user) performs the following multi-tab UAT in a real browser — Claude does NOT execute these steps. Wait for the developer's confirmation per the `<resume-signal>` block at the end.

    Pre-step: have BOTH a v5 build (on `main`) and the v6 build (this phase-12 branch) buildable on demand.

    1. Check out `main`. Run `npm install && npm run dev`. Open `http://localhost:4173` in Tab A. Confirm the app renders.
    2. In the SAME browser profile (same window OK, just a new tab), open a SECOND tab to `http://localhost:4173` as Tab B. Both tabs are now on v5, both have live IndexedDB connections.
    3. Optional sanity check: in DevTools → Console (Tab A), run `await window.indexedDB.databases?.()` (modern Chrome only) and confirm `3DCosterDB` shows `version: 5`. Skip if your browser does not expose this API.
    4. Without closing either tab, kill the dev server (Ctrl-C in the terminal).
    5. Switch to the phase-12 branch (this branch). Run `npm install && npm run dev` again. The dev server now serves the v6 bundle.
    6. In Tab A, hard-reload (Cmd-Shift-R / Ctrl-Shift-R) to load the v6 bundle. Tab A triggers Dexie's upgrade to v6 (the first call into `db` after hard-reload fires `db.open()` which sees v5 < v6 and runs the upgrade chain).
    7. WITHIN ~1 SECOND, Tab B (which still holds an open v5 connection) should auto-reload itself — observe the tab's reload spinner / favicon flicker / URL bar reload indicator.
    8. After Tab B finishes reloading, it should render the app normally on v6. The Console in Tab B should NOT show any `versionchange` warning from Dexie's default handler (because our handler ran first and reloaded the tab).
    9. In Tab B's DevTools → Application → IndexedDB → `3DCosterDB`, confirm `version: 6` (same database, same data, both tabs now on the v6 schema).

    Expected behaviour summary: Tab B reloads within ~1s of Tab A loading the v6 bundle; no white screen in either tab; both tabs end up on v6.

If still flaky, the registration site of `db.on('versionchange', ...)` may be racing with first `db.open()`; RESEARCH Pitfall 1 covers this — re-verify by grepping `src/db/database.ts` to confirm the handler is at module-top-level (NOT inside `useEffect`, `componentDidMount`, or any function).

|----------|-------------|

| Multi-tab IndexedDB `versionchange` event | A second tab on the v5 bundle holds an open connection; the v6 tab must trigger the cross-tab event AND the existing handler must fire AND `window.location.reload()` must succeed. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-12-04-01 | Denial of Service (data loss / partial migration) | Real-browser v6 upgrade transaction | mitigate | Task 2 sub-step 6 explicitly inspects every job record after the upgrade.
