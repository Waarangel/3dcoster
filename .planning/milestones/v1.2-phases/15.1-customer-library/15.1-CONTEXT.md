# Phase 15.1: Customer Library - Context

**Gathered:** 2026-05-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Customers become first-class records in their own Dexie store. A new top-level "Customers" tab in the main nav lists saved customer records (Name, Email, Company, Address, Notes, Last used) with create / edit / delete affordances and a bulk CSV importer. The Record Sale modal in `JobsManager.tsx` grows a "Select existing customer" combobox above the existing 4-field Customer block; picking a saved customer fills the four fields (still editable per D-21 from Phase 14). Per-Sale customer data remains a by-value snapshot — historical sales are byte-identical after a library customer is edited or deleted. The new store ships in a Dexie v6 → v7 migration with no row backfill (the store starts empty).

**In scope:**
- New `Customer` interface in `src/types.ts` extending `JobCustomer` with `id: string`, `createdAt: Date`, and optional `lastUsedAt?: Date`. Reuses the existing five-field shape (name/email/company/address/notes — `notes` already lives on `JobCustomer` from Phase 14's 2026-05-22 follow-up).
- New `customers` Dexie store at v7 with schema string `'id, name, email, lastUsedAt'` (email is a non-unique index for fast lookup). v6 → v7 migration is a no-op for existing data (no row backfill). `versionchange` reload handler from SCHEMA-02 already covers v7.
- `useCustomers()` entity hook in `src/hooks/useDatabase.ts` modeled on `useAssets()` — `useLiveQuery` over `db.customers.toArray()`.
- New top-level tab `'customers'` added to the `Tab` union in `src/App.tsx` and wired into the tab nav + activeTab switch. Tab label: "Customers" (full) / "Customers" (short — same).
- New `src/components/CustomerLibrary.tsx` modeled on `AssetLibrary.tsx`: heading + actions row (Add customer / Import CSV), free-text search input filtering on Name + Email + Company (case-insensitive substring), virtualized `react-window` list using `useDynamicRowHeight`, empty-state via existing `<EmptyState>` primitive.
- New `src/components/CustomerEditModal.tsx`: 5-field form (Name → Email → Company → Address → Notes), used for both create and edit. Save closes the modal; Cancel discards.
- New `src/components/CustomerCsvImportModal.tsx`: sibling to `CsvImportModal.tsx`, two-step Upload → Preview flow. Required: Name OR Email (row rejected if both empty). Columns accepted: `name`, `email`, `company`, `address`, `notes` (case-insensitive headers, order irrelevant). Preview shows N rows + validation errors + a single radio `Skip duplicates` (default) vs `Update duplicates`. Update = merge (overwrite only non-empty incoming fields).
- New `src/utils/customerCsv.ts` parser modeled on `csvHelpers.ts` — keeps customer parsing isolated from asset parsing.
- Combobox picker in `JobsManager.tsx` Record Sale modal: a single text input above the 4 Customer fields that filters the customer list as the user types (Name OR Email substring, case-insensitive). Picking a row fills Name/Email/Company/Address (Notes is NOT auto-filled into the sale form — Notes lives only on the library record). On pick, bump `customer.lastUsedAt = new Date()` and persist.
- "Add new" inline behavior: on Save sale, if the user typed values without picking, auto-create a Customer library record (only when Name OR Email is non-empty). Email-match dedup: if `email.trim().toLowerCase()` matches an existing library record, silently link to that record (bump `lastUsedAt`, do NOT create a duplicate, do NOT overwrite library fields with the per-sale typed values).
- Delete confirmation: native `confirm('Delete {name}? They appear in {N} past sales — those sales will keep the buyer details on record (this only removes them from your library).')`. The N is a one-shot count from a scan of `db.sales` matching by email (case-insensitive) at click time.
- `src/features.ts` entry `customer-library` dated to the actual ship date. `<NewBadge feature="customer-library">` placed as absolute overlay on the new "Customers" tab in main nav (per project memory rule — never inline, always absolute corner).

**Out of scope:**
- White-label / paid-tier customer features (CSV export, sync, multi-device) — deferred to paid milestone
- Customer-bound metrics / dashboards / "total spent" or "lifetime value" computed columns — out of v1.2 scope; deferred to a later Sales Pipeline milestone
- Sortable column headers / advanced filters on the Customers tab — search is sufficient at v1
- Tag autocomplete / customer groups / segments — out of scope
- Soft-delete / archive workflow — delete is permanent (locked: by-value snapshots make this safe)
- Editing the library record from inside the Record Sale modal (the modal only picks; the user goes to the Customers tab to edit a saved record)
- Phase 16 PDF rendering — Phase 16 reads the Sale snapshot; it does NOT need to know about the library
- Genericizing `CsvImportModal` into a polymorphic generic — sibling `CustomerCsvImportModal` is the chosen approach
- Any change to the existing `JobCustomer` shape (the library record extends it; the existing shape is untouched)
- Dexie schema changes outside the new `customers` store (no edits to existing stores in v7)

</domain>

<decisions>
## Implementation Decisions

### Customer Record Shape & Store
- **D-01:** New interface `Customer extends JobCustomer { id: string; createdAt: Date; lastUsedAt?: Date }` in `src/types.ts`. Same five fields (name/email/company/address/notes) flow into the per-Sale snapshot with zero field mapping — `sale.customer` is literally `{name, email, company, address, notes}` of whatever's in the Record Sale form at submit. Rejected: defining a new flat `Customer` interface (forces field-mapping forever) and reusing `JobCustomer` directly with an added `id` (pollutes the snapshot and risks devs treating `id` as a foreign key, blurring the by-value rule).
- **D-02:** `customers` is a new Dexie store added in v6 → v7 with schema string `'id, name, email, lastUsedAt'`. Email is a **non-unique** secondary index — fast lookup for dedup/picker, but never throws `ConstraintError` on duplicate. The v7 upgrade callback is a no-op (no row backfill needed; the store starts empty). The existing `versionchange → window.location.reload()` handler from Phase 12 SCHEMA-02 already covers v7.
- **D-03:** `lastUsedAt: Date` is a **stored** field on the Customer record, written ONLY when the user picks the customer in the Record Sale modal combobox (or when the silent-link path fires on email-match auto-save). Edits on the Customers tab do **not** bump `lastUsedAt` — the field means "last used in business," not "last touched." Rejected: computing `lastUsedAt` from the sales table on each render (O(sales) per row; fuzzy email-match is the only link in a by-value world).

### Picker UX in Record Sale
- **D-04:** Picker = single-input **combobox with typeahead**. The input lives directly above the existing 4-field Customer block in `JobsManager.tsx` Record Sale modal. As the user types, a dropdown of `<button>` rows shows up to N matches (planner picks N — e.g., 8 — with a "showing first 8 of M" footer if M > 8). Match logic: case-insensitive substring on `name` OR `email`. Each dropdown row shows `Name` (bold) on the top line and `email · company` on the muted second line. Clearing the input collapses the dropdown. No new deps — controlled `<Input>` + a filtered `useMemo` over `useCustomers()`. Rejected: native `<select>` (doesn't scale past ~50, no email visibility) and modal picker (extra click, breaks the single-modal flow of Record Sale).
- **D-05:** On pick: fill `Name`, `Email`, `Company`, `Address` from the picked record. Fields remain **editable** so the user can override per-sale (e.g., one-off shipping address). On submit, `sale.customer` captures whatever is in the form (may diverge from the library — library is NOT auto-updated from per-sale edits). `Notes` is **not** copied into the Record Sale form because Sale already has its own `notes` field (`Sale.notes`) for transaction notes; the customer's library notes live only on the library record. Locked by ROADMAP success criterion #3 ("still editable").
- **D-06:** "Add new" inline = **auto-save on submit**. If the user types into the four Customer fields without picking and then saves the sale, a new Customer library record is created (only if `Name` or `Email` is non-empty). No extra checkbox, no extra modal — the typeahead is the typo-prevention. Sale.customer snapshot is written in the same transaction. Rejected: explicit "Save to library" checkbox (friction every sale) and explicit "Add new" button in the combobox (extra click; doesn't match the "inline" language in the ROADMAP).
- **D-07:** When typed Email matches an **existing** customer (after `trim().toLowerCase()`), do NOT create a duplicate: silently treat it as if that customer was picked. Bump `lastUsedAt`. The per-sale typed values (e.g., a different address) flow to the Sale snapshot but do NOT overwrite the library record (consistent with the by-value rule — library is not auto-updated from per-sale edits). Rejected: silently overwriting the library on email-match (surprising; hard to undo) and showing a "use existing / create new" confirm dialog (friction defeats the design).

### CSV Import + Conflict Resolution
- **D-08:** Build new `src/components/CustomerCsvImportModal.tsx` as a sibling of `CsvImportModal.tsx`. Same Upload → Preview two-step flow, same outer chrome, but customer-specific parser, validator, row renderer, and submit handler. The existing `CsvImportModal` is deeply asset-shaped (currency, category, packageCost, ParsedRow, buildAssetsForImport) — genericizing it would be a meaningful refactor with risk to a shipped feature. Sibling approach is ~200–300 LOC of new code; justified. Parser lives in `src/utils/customerCsv.ts` (sibling to `csvHelpers.ts`). Rejected: genericizing into `CsvImportModal<T>` (out of scope, refactor risk) and the dropzone-primitive halfway path (shared piece is too small to justify a new primitive in `ui/`).
- **D-09:** Required columns: **Name OR Email**. A row with both name and email empty is rejected with an inline error in the preview. All five columns are accepted: `name`, `email`, `company`, `address`, `notes`. Header matching is case-insensitive. Column order doesn't matter. Missing columns just leave the field undefined on the resulting record. Rejected: hard-requiring Name (kills email-only Stripe imports) and hard-requiring Email (kills cash-buyer / in-person workflows).
- **D-10:** Email-match conflict resolution = **single global radio** in the Preview step: `Skip duplicates` (default) vs `Update duplicates`. Applied to ALL email matches in the file in one shot. Mirrors the existing CsvImportModal's `duplicateMode` pattern. Rejected: per-row dropdown in the preview (tedious for 50+ conflicts) and "always skip, no toggle" (explicitly contradicts ROADMAP success criterion #2 which says "skipped or updated per user choice").
- **D-11:** When the user picks `Update duplicates`: **merge** semantics — overwrite only the library fields that are **non-empty** in the incoming CSV row. Empty CSV cells preserve the existing library value. So re-importing a Stripe `customers.csv` with only `name` and `email` does not nuke the manually-typed `notes` and `address` on existing records. Treats imports as additive, not destructive. Rejected: replace-all (re-importing a partial export wipes data, nasty surprise) and "only fill blanks" (most user expectation of "update" is "replace this value with the new one").

### Customers Tab UI & Delete
- **D-12:** Tab layout **mirrors AssetLibrary**. New `src/components/CustomerLibrary.tsx`: heading + action buttons (Add customer / Import CSV) on top, then a free-text search input, then a virtualized `react-window` list using `useDynamicRowHeight`. Row layout: Name (bold) on top line; `email · company` on muted second line; `Last used: {relative date}` on the right; Edit + Delete buttons on the far right. Empty state via existing `<EmptyState>` primitive when zero customers exist. Mobile collapses to single-column. Pro: zero design debt, perf budget already paid by Phase 11. Rejected: non-virtualized list (ROADMAP says "virtualized") and sortable-table view (net-new pattern for the app; deferred).
- **D-13:** Edit and Create both use a **modal** (`src/components/CustomerEditModal.tsx`) with the 5-field form (Name → Email → Company → Address → Notes). Reasons inline editing is rejected: multi-line Address + Notes don't squeeze cleanly into a virtualized row; react-window's `useDynamicRowHeight` would need to handle a much taller row, causing neighbor jumps. Modal is reused for both "Add customer" and per-row "Edit" — one source of truth for the form layout. Same chrome and primitives as existing modals (`<Input>`, `<Textarea>`, `<Button>`).
- **D-14:** Delete = native `confirm()` with a sale-reference count. Copy: `Delete {name}? They appear in {N} past sales — those sales will keep the buyer details on record (this only removes them from your library).` The `N` is computed on click from a one-shot scan of `db.sales` matching by `customer.email.toLowerCase()` (case-insensitive). Acceptable cost — only fires on a delete click. Pro: defuses the "wait, will I lose my sales history?" panic on the first delete. Rejected: plain `confirm()` without count (misses the reassurance) and custom modal with "View sales" link (way more scope; user can already navigate to Jobs tab).
- **D-15:** Search input filters across **Name + Email + Company** (case-insensitive substring). Matches the picker's filter scope so users build the same mental model on both surfaces. Rejected: searching all 5 fields including Address + Notes (noisy false-positives; "st" matches every "street") and Name + Email only (Company is a common way users remember buyers — "the Acme guy").

### NEW Badge & Wiring
- **D-16:** Single `src/features.ts` entry `customer-library` dated to the actual ship date (planner writes the date when the phase ships, not the discussion date). Consumed by a single `<NewBadge feature="customer-library">` placed as an **absolute overlay** on the new "Customers" tab button in main nav (`<button className="relative">` host + `<NewBadge className="absolute -top-1 -right-1 pointer-events-none">`). Project memory rule: NEW badge must NEVER push, wrap, shrink, or reflow siblings — main nav is a flex row of tabs, so inline placement would break the layout. Tab nav uses `pointer-events-none` on the badge so the underlying button stays clickable. The picker combobox and CSV import button do NOT get their own badges (they're surfaces of the same feature; the tab badge is the entry point).

### Claude's Discretion
- Combobox dropdown match-limit (D-04 mentions N=8 as a reasonable default; planner finalizes)
- Default sort order on the Customers tab list (recommend `lastUsedAt desc` with NULL-last so brand-new never-used customers appear at the top — symmetric to "newest first" intuition; planner picks)
- How "Last used" renders on the row when `lastUsedAt` is undefined ("Never used" vs em-dash vs blank — planner picks; "Never used" is most readable)
- Exact relative-date format for "Last used" ("3 days ago" vs "2026-05-19" vs both; reuse any existing date helper if one exists in `src/utils/` — otherwise planner picks a minimal `Intl.RelativeTimeFormat` approach with no new deps)
- Mobile-vs-desktop affordance for Edit/Delete buttons (icon-only on mobile, label+icon on `sm+`)
- Whether the CustomerEditModal closes on Save success or stays open with a "Saved" toast (recommend close — matches existing asset-edit flow)
- Validation error wording in the CSV importer preview ("Both Name and Email are empty" / "Email format invalid (no @)" — planner copy-edits; the field-set is fixed by D-09)
- Whether the CSV importer accepts both `address1` + `address2` columns or only a single `address` column (recommend single only — `JobCustomer.address` is a freeform string anyway; planner sticks with single)
- Whether the CSV importer normalizes email to lowercase on write (recommend yes — keeps stored data consistent with the dedup-key, which is `toLowerCase()`)
- Exact Tailwind classes for the new dropdown panel under the combobox (`absolute z-10 mt-1 bg-slate-800 border border-slate-700 rounded-lg shadow-lg max-h-72 overflow-y-auto` is a reasonable starting point; planner picks)
- Test coverage strategy: a unit test for `customerCsv.parseRows` covering the duplicate-merge rule + a unit test asserting that editing a library record does NOT mutate a fixture Sale's `customer` snapshot (this latter test is locked by ROADMAP success criterion #4 — by-value audit)
- Whether `useCustomers()` exposes a memoized email→customer map alongside the array (recommend yes — picker + dedup both want O(1) email lookup)

</decisions>

<specifics>
## Specific Ideas

- The CSV columns map 1:1 to JobCustomer fields by header name (`name`, `email`, `company`, `address`, `notes`) — no field renaming or mapping UI. This intentionally diverges from common CRM exports (which might use `first_name`/`last_name`) — the user can re-export from their CRM with merged name or paste into Excel to combine. Keeps the importer simple.
- The picker dropdown row layout: `Name` bold on line 1, `email · company` muted on line 2 — three-data lookup in one line preserves vertical density while still helping the user disambiguate two `Jane Smith`s.
- Delete confirmation copy explicitly reassures: "those sales will keep the buyer details on record." This wording is intentional — first-time deleters need to know the by-value snapshot architecture without having to think about data models.
- The `lastUsedAt` field is deliberately NOT bumped by library edits — sorting by recency should reflect business activity, not when the user touched the record.

</specifics>
