# Phase 15.1: Code Review Report

**Reviewed:** 2026-05-22
**Depth:** standard
**Files Reviewed:** 13

## Summary

Phase 15.1 delivers a Customer Library with a Dexie v7 migration, useCustomers hook, CustomerLibrary tab, CSV importer, and a combobox picker in the Record Sale modal. The by-value snapshot rule (CL-05) and Notes preservation lock (D-05) are correctly implemented. The Dexie v7 migration is genuinely additive. The CSV parser correctly enforces "name OR email" and merge semantics. NewBadge is placed only on the Customers tab as an absolute overlay.

No BLOCKER findings. The CL-05 by-value rule is honored end-to-end — `JobsManager.handlePickCustomer` does not write through to `sale.customer`, library customer records are never read at sale-render time (the recent-sales display in `JobCard` reads `sale.customer.*` only), and the auto-link path correctly avoids overwriting library fields with per-sale typed values (D-07).

12 WARNING / INFO findings cluster around: combobox accessibility edge cases (Enter on no-match, missing `aria-label` on input, no listbox `aria-labelledby`), an unhandled-promise pattern in JobsManager's confirm-delete flow, a memoization regression in `CustomerLibrary.handleDelete` (deps array missing `db` even though `db` is module-scope — actual issue is N+1 risk by reading all sales every delete), a sort-stability issue where mutating a Dexie-returned array passes mutations to consumers, and a few D-15 / D-11 edge cases. No security vulnerabilities found (no XSS sinks, no injection, no hardcoded secrets, no insecure crypto).

## Warnings

### WR-01: Combobox Enter on empty filter inserts unhandled keystroke into form submit chain

**File:** `src/components/JobsManager.tsx:579-585`
**Issue:** When the picker dropdown is open but `visibleCustomers` is empty (user typed a query that matches nothing), pressing `Enter` falls through to the comment-noted "let Enter submit the form (existing behavior)". But the Record Sale modal's `<div>` wrapper is not a `<form>` — there's no implicit submit handler. Worse, the dropdown stays open showing "No saved customers match…" yet `Enter` does nothing visible; users expect Enter to either pick the first match (none here) or close the suggestion list. Currently it just no-ops.

```tsx
} else if (e.key === 'Enter') {
  const picked = visibleCustomers[customerPickerActiveIndex];
  if (customerPickerOpen && picked) {
    e.preventDefault();
    void handlePickCustomer(picked);
  }
  // else: let Enter submit the form (existing behavior) ← but there's no <form>
}
```

**Fix:** Treat Enter-with-no-match as "dismiss the dropdown" to give users a clear next step.

```tsx
} else if (e.key === 'Enter') {
  if (customerPickerOpen) {
    const picked = visibleCustomers[customerPickerActiveIndex];
    if (picked) {
      e.preventDefault();
      void handlePickCustomer(picked);
    } else if (customerPickerQuery.trim()) {
      // No match — close suggestions so the user can fill the fields below.
      e.preventDefault();
      setCustomerPickerOpen(false);
    }
  }
}
```

### WR-02: `handleDelete` reads ALL sales into memory on every customer delete

**File:** `src/components/CustomerLibrary.tsx:180-193`
**Issue:** The delete-confirmation count uses `db.sales.toArray()` then filters in-memory. For a user with thousands of sales, this loads the entire sales table to count matches by one email — O(sales) memory + transfer. The `customers` store already has a non-unique `email` index, and `sales` does not, but `db.sales.where('jobId')` style filtering exists elsewhere. The minimum fix is to bind the predicate to the index path. (Performance is listed out of scope, but this is a correctness-adjacent issue: on a low-end mobile device with a large IndexedDB this can lock the UI thread for seconds while serializing all sale records.)

**Fix:** Use a Dexie filter that walks the store rather than materializing it.

```tsx
const handleDelete = useCallback(async (customer: Customer) => {
  const emailKey = (customer.email || '').trim().toLowerCase();
  const n = emailKey
    ? await db.sales
        .filter(s => (s.customer?.email || '').trim().toLowerCase() === emailKey)
        .count()
    : 0;
  // …rest unchanged
}, [onDeleteCustomer]);
```

This still walks every sale (no email index on the sales store), but `.count()` doesn't allocate the array, and Dexie streams the iteration.

### WR-03: `sortedCustomers` mutates the shared `customers` reference indirectly via `arr.sort`

**File:** `src/components/CustomerLibrary.tsx:126-139`
**Issue:** `const arr = [...customers];` shallow-clones the array, so `arr.sort(...)` is safe for the outer array. Good. However `customersByEmail` in `useDatabase.ts:552-559` iterates `customers ?? []`, and several other consumers (JobsManager picker) also rely on the array reference being stable. The current pattern is fine for sorting purposes, but the `[...customers]` clone happens every `customers` change — which means a new `sortedCustomers` array on every Dexie liveQuery emission, which then cascades into a new `searchedCustomers`, which then cascades into a new `listRowProps`. That's expected. The real concern: `customers` itself is the raw Dexie-returned array. If any other code path elsewhere ever mutates `customers` in place (e.g., a future `customers.sort()` in another component), it would corrupt the Dexie cache. No bug today, but the lack of `Object.freeze(customers)` at the hook boundary is a footgun waiting to be tripped.

**Fix:** Defensive — return a frozen wrapper at the hook boundary:

```ts
return {
  customers: customers ?? [],
  // …
};
```
Could become:
```ts
const customersFrozen = useMemo(
  () => Object.freeze(customers ?? []),
  [customers]
);
```
Acknowledged that this is "should be done" not "must be done" — flag as WARNING only because the next reviewer should know this is a paved path for a hard-to-find bug.

### WR-04: `handlePickerKeyDown` ArrowDown ignores `visibleCustomers === 0` and opens an empty dropdown

**File:** `src/components/JobsManager.tsx:562-572`
**Issue:** If the user types a query that has zero matches, then presses ArrowDown, the handler unconditionally opens the dropdown (`setCustomerPickerOpen(true)`) even though `visibleCustomers.length === 0`. The visible result is "the empty-state row appears, with active index 0 pointing nowhere." Combined with WR-01, pressing Enter immediately after does nothing.

**Fix:** Guard the open path on having matches, OR allow the open state but treat the empty case visually (which already exists). Cleanest fix:

```tsx
if (e.key === 'ArrowDown') {
  e.preventDefault();
  if (visibleCustomers.length === 0) return;  // nothing to navigate
  if (!customerPickerOpen) {
    setCustomerPickerOpen(true);
    setCustomerPickerActiveIndex(0);
  } else {
    setCustomerPickerActiveIndex(i => (i + 1) % visibleCustomers.length);
  }
}
```

### WR-05: D-07 auto-link path bumps `lastUsedAt` twice when the user picks AND email matches

**File:** `src/components/JobsManager.tsx:548-558` and `:639-644`
**Issue:** `handlePickCustomer` calls `bumpLastUsed(c.id)` (line 557) when the user clicks a row. Then in `handleRecordSale`, the auto-link block at line 639 fires when the user submits — `editingSale` is falsy, `customer` is truthy, `customer.email` is truthy → it looks up the existing record by email and `bumpLastUsed(existing.id)` fires AGAIN. Functionally idempotent (the `Date` write overwrites itself within a few seconds), but it's a redundant write and the second bump can race with the first. If the user picked customer A then edited the email field to customer B's email before submit, the auto-link bumps B (which is the correct behavior per D-07), and A's lastUsedAt was already bumped by the pick (which is now incorrect — A wasn't actually "used in business" for this sale). The current code can't distinguish those cases.

**Fix:** Track whether the current sale was "picked" (a `pickedCustomerId` ref / state) and skip the auto-link branch when the picked-and-email-still-matches case is true. Or simpler: only call `bumpLastUsed` from `handleRecordSale` (not from `handlePickCustomer`) — the bump should fire at sale-commit time, not at pick time. Picking without saving (user clicks pick then cancels) currently corrupts `lastUsedAt`, which is the same root cause.

```tsx
// In handlePickCustomer: drop the await bumpLastUsed line.
// In handleRecordSale: the auto-link branch already handles bump-on-commit correctly.
```

### WR-06: CSV importer "file too large" / "binary file" cases produce confusing errors

**File:** `src/components/CustomerCsvImportModal.tsx:69-95`
**Issue:** `processFile` only validates by file extension (`.csv` suffix). If a user drops a 200MB log file renamed to `.csv`, `file.text()` reads the whole thing into memory and the Papa parser walks every row before returning. There's no size cap and no MIME-type check. On a low-RAM device this can crash the tab. Similar issue: a `.csv` that is actually binary (a stray Excel file with `.csv` extension that's really XLSB) silently parses as one giant header row with zero data rows and surfaces `"CSV file is empty"` from `parseCustomerCsv` even though the file has bytes.

**Fix:** Add a soft size cap and a sane empty-after-parse message.

```tsx
const MAX_CSV_BYTES = 5 * 1024 * 1024; // 5MB
// …
if (file.size > MAX_CSV_BYTES) {
  setError(`File is ${(file.size / 1024 / 1024).toFixed(1)} MB. Keep customer CSVs under 5 MB — split a larger file into smaller batches.`);
  return;
}
```

And in `parseCustomerCsv`, distinguish "empty after parse" vs "binary file with one weird row" via a header-validity check (none of the five expected headers present → "Could not find any of: name, email, company, address, notes columns").

### IN-01: `useCustomers` `isLoading` only flips on first count; never re-flips if the store is cleared

**File:** `src/hooks/useDatabase.ts:540-546`
**Issue:** The pattern matches `usePrinterInstances` (consistent), but `isLoading` is `true` until the first `db.customers.count()` resolves, then stays `false` forever. If a user clears IndexedDB via DevTools mid-session, the live query emits `undefined` briefly while `isLoading` is `false` — consumers see `customers: []` for a render. Same issue exists in the other entity hooks; it's a pre-existing pattern, not new to this phase. Flag for awareness.

**Fix:** Consider deriving `isLoading` from `customers === undefined` instead of the one-shot count.

```ts
const isLoading = customers === undefined;
// (drop the useState + useEffect)
```

### IN-02: `formatRelativeDate` is invariant on locale — uses hardcoded `'en'`

**File:** `src/utils/formatRelativeDate.ts:4`
**Issue:** `new Intl.RelativeTimeFormat('en', ...)` — hardcoded to English. The rest of the app does not appear to support locales, but if the project ever adds i18n, this `'en'` is a debt point. Project memory does not list i18n as a roadmap item, so the issue is informational.

**Fix:** Use the user's browser locale via `navigator.language` or accept a locale prop.

### IN-03: `CustomerEditModal` form has labels marked "Name *" and "Email *" but neither is individually required

**File:** `src/components/CustomerEditModal.tsx:133, 143`
**Issue:** Both labels include the `*` required marker, but the validation rule (line 71) is "Name OR Email" — neither is individually required. Users will read the asterisks as "both required," try to type only one, see the error message that says "Provide at least one of Name or Email", and feel confused. The helper text at line 122 says "Provide at least one of Name or Email" which conflicts with the `*` markers. Either remove the asterisks or change them to a different visual marker (e.g., the helper text alone, or an asterisk on a parent group).

**Fix:** Drop the asterisks on each label, keep the helper-text line.

### IN-05: `RowItem` (CSV importer preview) does not memoize and re-renders all rows on every toggle

**File:** `src/components/CustomerCsvImportModal.tsx:423-484`
**Issue:** `PreviewStep` maps over `parseResult.rows` and renders `<RowItem>` for each — the `onToggle` prop is `() => onToggleRow(row.rowNumber)` (new arrow each render). For 1,000-row imports, toggling one row re-renders all 1,000 rows. Not a correctness issue, but the parent already establishes the pattern of wrapping rows in `React.memo` (see CustomerLibrary). RowItem can be `React.memo` with `onToggle: (rowNumber) => void` taking the row number explicitly. Performance is out of scope for v1, but flagged because the existing project pattern is to memoize.

### IN-06: `customerPickerInputRef` is declared but never read

**File:** `src/components/JobsManager.tsx:388`
**Issue:** `customerPickerInputRef` is assigned to the picker `<Input ref=...>` (line 856) but never `.current.focus()`'d or otherwise consumed. If the intent was to autofocus the picker when the modal opens, that's missing. If there's no intent, remove the ref. TypeScript's `noUnusedLocals` doesn't catch this because the ref IS used (passed as `ref={}`), but it never produces a behavior.
