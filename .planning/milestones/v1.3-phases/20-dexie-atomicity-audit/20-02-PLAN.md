<objective>
Move the `nextQuoteNumber` read in `createQuote` (`src/hooks/useDatabase.ts:841-907`) from the React state argument (L843: `const nextNum = userProfile.nextQuoteNumber ?? 1;`) to a `tx.table('settings').get('userProfile')` call INSIDE the existing 3-store transaction body (L893). Two tabs reading the same React snapshot today both compute the same `nextNum` and write the same `quoteNumber` — moving the read inside the tx eliminates this race per D-05 (CONTEXT.md decision #5).

Purpose: Close CODE-AUDIT #11 (DATA-02, MEDIUM severity — concurrent-tab quote-number collisions). The existing transaction already includes `db.settings` in its table list; only the read site changes. The React `userProfile` argument continues to be the source of truth for `currency`, `defaultTaxRate`, `defaultTerms`, `address`, `defaultProfitMargin` — ONLY `nextQuoteNumber` changes source.

Output: The transaction scope function gains a `tx` parameter (`async (tx) => { ... }`); a `tx.table('settings').get('userProfile')` read at the top of the body computes `nextNum` from the tx-scoped snapshot; the existing `setUserProfile(...)` write at the bottom of the body stays unchanged (it already participates in the open transaction zone). One new unit test in `src/hooks/useDatabase.test.ts` asserts the call order (`tx.table('settings').get` before `db.quotes.add`). A manual two-tab UAT script is documented in this plan and executed once; automated concurrent-tab test deferred to Phase 23 TEST-04 (`fake-indexeddb`).
