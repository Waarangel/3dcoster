## Summary

Phase 22.1 reconciles two break-even formulas that compute different numbers for the same saved job: the Calculator widget includes `modelCost + printerDepreciation + nozzleWear` in the numerator while JobsManager's `computeBreakEvenInfo` uses only `modelCost`. The fix has three components: (1) persist a `fixedCostsAtSave` snapshot on `PrintJob` at save time by reading from the `fixedCosts` memo already in scope in both `CostCalculator.tsx` save paths; (2) switch `computeBreakEvenInfo`'s numerator from `job.modelCost` to `job.modelCost + (job.fixedCostsAtSave?.depreciation ?? 0) + (job.fixedCostsAtSave?.nozzleWear ?? 0)`; and (3) ship a one-time pure reconcile helper that backfills the snapshot onto legacy jobs using the existing `printerInstances` records.

The reconcile invocation site is `useJobs()` in `src/hooks/useDatabase.ts`, NOT App.tsx. The existing reconciles (`reconcileCopiesSoldFromSales`, `normalizeTagsOnJob`) use **module-level boolean flags** for process-lifetime idempotency — there is no Dexie `meta` table in this codebase. CONTEXT.md D-08 mentions a "Dexie meta-row flag" but this does not exist; the planner MUST use the module-flag pattern instead. The formula for depreciation is `purchasePrice / (recoveryMonths × monthlyHours) × printTimeHours`; the formula for nozzleWear is `(totalFilamentVolumeCm3 / nozzleLifespanCm3) × nozzleCost`. Neither applies the `failureRate` multiplier — that only applies to per-unit consumable costs.

Two WR carry-overs are bundled: WR-01 removes the dead `userProfile` prop from `RecordSaleModalProps` (declared at line 60, passed at JobsManager.tsx:1406, never destructured/read inside the component); WR-02 drops `job.sellingPrice` from the hydration `useEffect` dep array at `RecordSaleModal.tsx:155`.

**Primary recommendation:** Mirror the `reconcileCopiesSoldFromSales` module-flag pattern in `useJobs()`. Add `reconcileFixedCostsAtSave` to `backfill.ts`. Add tests to the existing `backfill.test.ts` (584 lines — large but coherent; a new file for only one new helper would add overhead without clarity benefit).

### Pattern 1: Module-Level Flag Reconcile (the canonical invocation pattern)

**What:** A module-level boolean flag gates a `useEffect` inside a hook so the reconcile runs exactly once per page load. The flag lives outside the component tree so React remounts don't re-trigger it.

**When to use:** Every one-time startup reconcile in this codebase.

**Example (from `useDatabase.ts` — existing `reconcileCopiesSoldFromSales` at lines 458–488):**
```typescript
// [VERIFIED: src/hooks/useDatabase.ts:16]
let copiesSoldReconcileRan = false;  // module-level (survives remounts)

// Inside useJobs():
useEffect(() => {
  if (copiesSoldReconcileRan) return;
  if (jobs === undefined) return;        // wait for first liveQuery emission
  copiesSoldReconcileRan = true;
  let cancelled = false;
  (async () => {
    try {
      const allSales = await db.sales.toArray();
      if (cancelled) return;
      const patches = reconcileCopiesSoldFromSales(jobs, allSales);
      if (patches.length > 0) {
        await db.transaction('rw', db.jobs, async () => {
          for (const patch of patches) {
            const current = await db.jobs.get(patch.id);
            if (current) {
              await db.jobs.put({ ...current, copiesSold: patch.copiesSold, updatedAt: new Date() });
            }
          }
        });
      }
    } catch (err) {
      console.error('copiesSold reconcile failed:', err);
      copiesSoldReconcileRan = false;  // allow retry on next mount
    }
  })();
  return () => { cancelled = true; };
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [jobs === undefined]);
```

**New reconcile flag name:** `fixedCostsReconcileRan` — follows the same naming convention.

### Pattern 2: Pure Reconcile Helper in backfill.ts

**What:** A pure function accepting plain arrays, returning updated objects. No Dexie, no React. Caller does the actual `bulkPut`.

**When to use:** All startup-triggered reconciles in this codebase.

**Exact function signature to mirror (from `reconcileCopiesSoldFromSales`):**
```typescript
// [VERIFIED: src/db/backfill.ts:413-431]
export function reconcileFixedCostsAtSave(
  jobs: PrintJob[],
  printerInstances: PrinterInstance[],
): PrintJob[] {
  // Build id→instance map for O(1) lookup
  const instanceById = new Map<string, PrinterInstance>();
  for (const inst of printerInstances) instanceById.set(inst.id, inst);

  const out: PrintJob[] = [];
  for (const job of jobs) {
    if (job.fixedCostsAtSave !== undefined) continue;  // already snapshotted — idempotent

    const inst = instanceById.get(job.printerInstanceId);
    if (!inst) {
      console.warn(`[reconcileFixedCostsAtSave] orphan job "${job.name}" (${job.id}): printerInstanceId "${job.printerInstanceId}" not found — snapshotting zeros`);
      out.push({ ...job, fixedCostsAtSave: { depreciation: 0, nozzleWear: 0 } });
      continue;
    }

    // Mirror calculateDepreciation() from src/utils/costCalc.ts:70-80
    // No failureRate multiplier — depreciation is NOT failure-adjusted
    const purchasePrice = inst.actualPurchasePrice ?? 0;
    const recoveryMonths = inst.recoveryMonths ?? 12;
    const monthlyHours = inst.estimatedMonthlyPrintHours ?? 40;
    const totalRecoveryHours = recoveryMonths * monthlyHours;
    const depreciationPerHour = totalRecoveryHours > 0 ? purchasePrice / totalRecoveryHours : 0;
    const depreciation = depreciationPerHour * job.printTimeHours;

    // nozzleWear requires filament volume + printer nozzle specs.
    // The reconcile helper does NOT have access to materials/filament densities,
    // so it cannot recompute nozzleWear faithfully (see Pitfall 1).
    // Fallback: snapshot 0 for nozzleWear on legacy jobs.
    // (See Pitfall 1 — this is the researched resolution.)

    out.push({ ...job, fixedCostsAtSave: { depreciation, nozzleWear: 0 } });
  }
  return out;
}
```

> **STOP: Pitfall 1 (nozzleWear in backfill) surfaces here — see Common Pitfalls.**

### Anti-Patterns to Avoid

- **Using a Dexie meta table for the reconcile flag:** There is NO `meta` table in this database. CONTEXT.md D-08 mentions "Dexie meta-row" but the actual pattern is a **module-level boolean** in `useDatabase.ts`. Adding a meta table would require a Dexie schema version bump — explicitly forbidden.
- **Applying failureRate to depreciation or nozzleWear in the backfill:** The failure multiplier (`1 / (1 - failureRate/100)`) is applied ONLY to per-unit consumable costs in `calculateCost`. `printerDepreciation` and `nozzleWear` are computed independently (fixed costs). The CONTEXT.md D-06 description of `depreciationPerHour * printTimeHours * (1 + failureRate)` is incorrect; use `depreciationPerHour * printTimeHours` only.
- **Putting the reconcile in App.tsx:** None of the existing reconciles are in App.tsx. They all live in `useDatabase.ts` hooks (specifically inside `useJobs()` and `useCustomers()`).
- **Mutating the liveQuery cache directly:** Always work on `{ ...job }` shallow copies, never mutate the job objects returned by `useLiveQuery`.

## Critical Finding: nozzleWear Formula vs. Backfill Capability

**This is the most important open question for the planner.**

CONTEXT.md D-06 states: "Backfill computes depreciation and nozzleWear from the same arithmetic the Calculator uses today." This is only half-true.

**Depreciation** can be reconstructed from `PrinterInstance` fields: `depreciationPerHour * printTimeHours` where `depreciationPerHour = actualPurchasePrice / (recoveryMonths * estimatedMonthlyPrintHours)`. All inputs are on the `PrinterInstance` and `PrintJob` records. [VERIFIED: costCalc.ts:70-80, PrinterInstance interface in types.ts:89-101]

**NozzleWear** cannot be faithfully reconstructed from `PrintJob` alone. The formula is:
```
nozzleWear = (totalVolumeCm3 / selectedPrinter.nozzleLifespanCm3) × selectedPrinter.nozzleCost
```
where `totalVolumeCm3 = sum(filament.grams / getMaterialDensity(filament.filamentType))` [VERIFIED: costCalc.ts:86-99]

The `nozzleLifespanCm3` and `nozzleCost` fields live on `PrinterConfig` (not `PrinterInstance`). The reconcile helper would need access to both `printerInstances` AND `printers` (PrinterConfig). Additionally, material density lookup requires `db.materials` for each filament in `job.filaments`.

**Three viable paths for the planner to choose from:**

**Path A — Snapshot zero for nozzleWear in backfill (simplest, D-07-analogous):**
- Backfill sets `fixedCostsAtSave.nozzleWear = 0` for all legacy jobs
- Forward savings from new jobs will be accurate
- Legacy jobs show break-even slightly lower than Calculator (nozzleWear is typically small: $0.01–$0.05)
- Consistent with D-07's "orphan job → zero snapshot" approach

**Path B — Pass printers + materials into the helper:**
- `reconcileFixedCostsAtSave(jobs, printerInstances, printers, materials)` — wider signature
- Faithfully reconstructs nozzleWear for all legacy jobs with valid printers
- Aligns most closely with D-06's intent

**Path C — Use `job.fixedCostsAtSave` from Calculator on next Save (forward-only for nozzleWear, zero for legacy):**
- Same as Path A, but with a comment explaining the limitation

The planner must make this call. Research recommendation: **Path B** is correct if D-06's intent ("same arithmetic the Calculator uses") is the governing constraint. Path A is acceptable if "close enough" is acceptable for the small nozzleWear amount. Both paths are idempotent and consistent with D-07.

## Common Pitfalls

### Pitfall 1: nozzleWear Backfill Requires printer + materials Data

**What goes wrong:** `reconcileFixedCostsAtSave(jobs, printerInstances)` with only two arguments cannot compute nozzleWear because the formula needs `PrinterConfig.nozzleLifespanCm3`, `PrinterConfig.nozzleCost`, and material density lookup.

**Why it happens:** `PrinterInstance` (what `printerInstanceId` references) has cost-recovery fields but NOT the nozzle spec fields — those are on `PrinterConfig`. The existing `calculateNozzleWear` function signature takes `selectedPrinter: PrinterConfig | undefined` [VERIFIED: costCalc.ts:86-99].

**How to avoid:** Either extend the helper signature to `(jobs, printerInstances, printers, materials)` and mirror `calculateNozzleWear` directly, OR document the limitation and snapshot nozzleWear as `0` for legacy jobs (consistent with D-07's orphan-job zero-snapshot approach).

**Warning signs:** A `reconcileFixedCostsAtSave` implementation that calls `nozzleCost` or `nozzleLifespanCm3` on a `PrinterInstance` object will be `undefined` — those fields don't exist on `PrinterInstance`.

### Pitfall 2: failureRate Applied to depreciation/nozzleWear

**What goes wrong:** Implementing the backfill formula as `depreciationPerHour * printTimeHours * (1 + failureRate/100)` — as described (incorrectly) in CONTEXT.md D-06.

**Why it happens:** CONTEXT.md D-06 describes the formula as `printerInstance.depreciationPerHour * job.printTimeHours * (1 + job.failureRate)`. This is incorrect — the Calculator's `calculateCost()` does NOT apply the failure multiplier to depreciation or nozzleWear. [VERIFIED: costCalc.ts:182-185 — failureMultiplier applied ONLY to `perUnitSubtotal`, which excludes depreciation and nozzleWear]

**How to avoid:** Use `depreciationPerHour * printTimeHours` only. The `failureRate` field on `PrintJob` is a percentage (e.g., `5` = 5%) used ONLY for per-unit consumable cost adjustment.

**Warning signs:** Any formula referencing `(1 + failureRate)` in the depreciation or nozzleWear computation path is wrong.

### Pitfall 3: Using a Dexie meta table that doesn't exist

**What goes wrong:** Adding `db.meta.get('phase22_1_breakEvenReconcileV1')` or using a `key/value` meta table.

**Why it happens:** CONTEXT.md D-08 mentions a "Dexie meta-row flag with key `phase22_1_breakEvenReconcileV1`". No such table exists. The database has these tables only: `materials`, `printers`, `printerInstances`, `jobs`, `sales`, `settings`, `customers`, `quotes`. [VERIFIED: database.ts:12-21]

**How to avoid:** Use a module-level boolean flag in `useDatabase.ts` exactly as all three existing reconciles do.

**Warning signs:** Any code referencing `db.meta` will fail at runtime with "no table 'meta'" Dexie error.

### Pitfall 4: Mutating the liveQuery cache

**What goes wrong:** Modifying job objects from `jobs` (the `useLiveQuery` result) in place before calling `bulkPut`.

**Why it happens:** `useLiveQuery` returns live proxy objects; mutating them corrupts Dexie's reactivity cache.

**How to avoid:** Always spread: `out.push({ ...job, fixedCostsAtSave: { ... } })` — the existing reconciles all do this.

### Pitfall 5: WR-01 — userProfile still in destructuring

**What goes wrong:** Removing `userProfile` from the `RecordSaleModalProps` interface but forgetting to remove it from the function destructuring signature at line 70.

**Why it happens:** The interface and the destructuring are separate sites. Currently `userProfile` is in the interface (line 60) but NOT in the function destructuring (lines 70-79) — the prop was never read, just passed through. [VERIFIED: RecordSaleModal.tsx:58-79]

**How to avoid:** Remove from both `RecordSaleModalProps` interface AND the callsite in `JobsManager.tsx:1406` where `userProfile={userProfile}` is passed.

### Pitfall 6: WR-02 — dep array comment must explain WHY

**What goes wrong:** Dropping `job.sellingPrice` from the dep array without a comment, causing future developers to "fix" it back.

**Why it happens:** The eslint-disable comment format is already used in `useDatabase.ts`. A bare `eslint-disable-line` without a Pitfall 3 explanation will confuse readers.

**How to avoid:** Add a comment above the dep array explaining: "DO NOT add job.sellingPrice — a concurrent useLiveQuery emission updating the price should NOT clobber the user's in-progress form state. Only editingSale/convertingFromQuote identity drives re-hydration." [Per D-09]

### Depreciation formula for backfill (mirroring costCalc.ts:70-80)

```typescript
// [VERIFIED: src/utils/costCalc.ts:70-80]
// PrinterInstance fields: actualPurchasePrice?, recoveryMonths?, estimatedMonthlyPrintHours?
const purchasePrice = inst.actualPurchasePrice ?? 0;   // Note: no fallback to PrinterConfig.purchasePrice
const recoveryMonths = inst.recoveryMonths ?? 12;
const monthlyHours = inst.estimatedMonthlyPrintHours ?? 40;
const totalRecoveryHours = recoveryMonths * monthlyHours;
const depreciationPerHour = totalRecoveryHours > 0 ? purchasePrice / totalRecoveryHours : 0;
const depreciation = depreciationPerHour * job.printTimeHours;
// NO failureRate multiplier — failureRate only applies to per-unit consumable costs
```

**NOTE on `actualPurchasePrice`:** The Calculator's `calculateDepreciation()` falls back to `selectedPrinter?.purchasePrice` (the `PrinterConfig` purchase price) when `actualPurchasePrice` is undefined. If the backfill helper only has `PrinterInstance`, it can only use `inst.actualPurchasePrice ?? 0`. If Path B (wider signature with `printers`) is chosen, the fallback `printers.find(p => p.id === inst.printerConfigId)?.purchasePrice` can be used to match the Calculator exactly.
