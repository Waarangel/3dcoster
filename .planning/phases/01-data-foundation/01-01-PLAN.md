<task type="auto" tdd="false">
  <name>Task 2: Add Dexie v4->v5 migration in src/db/database.ts</name>
  <files>src/db/database.ts</files>
  <action>
Edit src/db/database.ts to append the version 5 migration block immediately after the existing `db.version(4).stores({...})` block (before the `export { db }` line).

The migration must:
- Repeat ALL store definitions (same indexes as v4 — filaments[] is not indexed)
- Return the `modify()` promise from the upgrade callback (critical — missing `return` causes partial migration)
- Mutate the `job` object directly inside `modify()` (Dexie proxy pattern — do NOT use spread/assign)
- Handle both cases: job with valid filamentId and job without

```typescript
db.version(5).stores({
  materials: 'id, category, brand, filamentType, currency',
  printers: 'id, name',
  printerInstances: 'id, printerConfigId, nickname',
  jobs: 'id, name, createdAt, printerInstanceId',
  sales: 'id, jobId, soldAt',
  settings: 'key',
}).upgrade(tx => {
  return tx.table('jobs').toCollection().modify(job => {
    const hasFilament = job.filamentId && job.filamentId.trim() !== '';
    if (hasFilament) {
      job.filaments = [{
        filamentId: job.filamentId,
        grams: job.filamentGrams || 0,
        // pricePerGram intentionally omitted — form falls back to asset library price
      }];
    } else {
      job.filaments = [];
    }
    delete job.filamentId;
    delete job.filamentGrams;
  });
});
```

The `upgrade` callback receives untyped Dexie objects, so TypeScript will not produce errors here even though `PrintJob` no longer has `filamentId`/`filamentGrams` — the migration operates on raw IndexedDB records, not typed objects. This is correct and expected Dexie behaviour.

Do NOT change the `export { db }` statement. Do NOT change any existing version blocks. Do NOT change the helper functions below.

After writing the file, run `tsc -b` to confirm no NEW errors were introduced in database.ts itself. The existing consumer errors from Task 1 will still be present — that is fine.
