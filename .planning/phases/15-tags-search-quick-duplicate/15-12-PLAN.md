## Round 2 Decisions (new — sibling to D-01..D-15)

The Gap E acceptance contract requires Round 2 to resolve three open questions before plans are authored. These resolutions are LOCKED for execution.

### D-16 — Title-row overflow strategy with many tags

**Decision:** **WRAP CHIPS BELOW THE TITLE** when the row's flex content exceeds the available width. The `<div className="group flex items-center gap-3 flex-wrap">` wrapper carries `flex-wrap`; chips, the `+` affordance, and the Tag icon naturally wrap to a second line when the row is narrow.

**Rationale:**
- Honors the locked D-11 "render every tag, no max-visible cap" decision — no chips are ever hidden.
- Avoids inventing a second affordance (popover, "+N more" indicator) whose discovery cost is higher than just letting chips wrap.
- Mobile / 320px viewports degrade gracefully: chips wrap to multiple rows without horizontal scroll or truncation.
- The break-even pill sits LAST in the row order (chips wrap BEFORE it); the pill ends up on whichever line still has space, which is acceptable — the pill is informational, not actionable.

**Rejected alternatives:**
- Truncate with "+N more" pill → adds a hidden affordance just to view chips; conflicts with D-11.
- Horizontal scroll (`overflow-x-auto`) → works on touch but is awkward on desktop and hides discoverability of the `+`.

**Placeholder constant:** `ADD_TAG_PLACEHOLDER = "trending, popular, out of date"` — module-scope constant in JobsManager.tsx. Three usage-domain examples comma-separated, matching the user's verbatim refinement from Round 1 ("the placeholder should suggest the KIND of tags users might apply — status / popularity / lifecycle indicators").

### D-17 — Add-tag input width

**Decision:** **NARROW input (`max-w-[12ch]`, ~96px)** that does NOT grow to fill remaining row width. The inline `<input>` opens at a fixed narrow width so the title-row layout does not jump dramatically on open. Auto-focus on open; Enter commits; Escape cancels; blur commits IF the value is non-empty (else cancels — matches the title-rename blur semantic).

**Rationale:**
- Tag names are short by D-02 design (whitespace+alphanumeric+hyphen+underscore, capped at the natural reading width of a chip).
- A wide input would force the chevron + title + chip strip + Tag icon + break-even pill to reshuffle on every `+` click, which is visually jarring.
- 12ch (~96px) accommodates the longest plausible single-tag input ("out-of-date" = 11 chars) plus a 1-char buffer.

**Tailwind classes for the add-tag input:** `max-w-[12ch] px-2 py-0.5 text-xs rounded bg-slate-700 border border-slate-600 text-slate-200 placeholder-slate-500 focus:outline-none focus:border-blue-500`. Mirrors the existing chip vertical padding (`py-0.5`) and font-size (`text-xs`) so the input visually sits at the same baseline as the surrounding chips.

### D-18 — Tag icon hover affordance + NewBadge target

**Decision:** **KEEP THE TAG ICON; KEEP THE NEWBADGE TARGET.** The Tag icon next to the title-row affordances stays as a discoverability shortcut. Clicking the Tag icon calls `handleStartAddTag(job.id)` (it no longer opens a panel — there is no panel). The `<NewBadge feature="tags" className="absolute -top-1 -right-1 pointer-events-none" />` overlay stays on the Tag icon (the project memory rule: ONE badge per feature key — the Tag icon is the most stable hover target on the title row).

**Rationale:**
- Round 1 UAT preserved the Tag icon ("Tag icon hover affordance stays as a shortcut"); Gap E refinement only changes WHAT it opens.
- The Tag icon is a STABLE visual element (always rendered in the DOM, just at `opacity-0` until hover) → the NewBadge has a fixed positioning anchor, preventing the badge from disappearing as chips wrap.
- Alternative (re-target NewBadge to the `+` button) was considered and REJECTED: the `+` is conditional (hidden when `tags.length === 10`), so the badge would vanish on max-tagged jobs. The Tag icon never disappears.
- Alternative (re-target NewBadge to the chip strip container) was considered and REJECTED: chips are conditional rendering (empty when `tags` is undefined/empty), so the badge would vanish on un-tagged jobs.

**Net result:** `feature="tags"` NewBadge JSX consumer count remains EXACTLY ONE in JobsManager.tsx and ZERO in CostCalculator.tsx (preserves Gap A removal). Three NewBadge consumers in JobsManager total: `tags` + `search-jobs` + `pdf-quote`. Zero `quick-duplicate` (preserves Gap D removal).

```ts
// Title edit-in-place
const handleStartEditTitle = useCallback((jobId: string) => {
  setEditingTitleJobId(jobId);
}, []);

const handleCancelEditTitle = useCallback(() => {
  setEditingTitleJobId(null);
}, []);

const handleSaveTitle = useCallback(async (job: PrintJob, name: string) => {
  const trimmed = name.trim();
  const safeName = trimmed.length > 0 ? trimmed : job.name;  // empty-name guard preserved
  // Only persist if the name actually changed — avoids a noop write + updatedAt bump.
  if (safeName !== job.name) {
    await db.jobs.put({ ...job, name: safeName, updatedAt: new Date() });
  }
  setEditingTitleJobId(null);
}, []);

// Add-tag inline input
const handleStartAddTag = useCallback((jobId: string) => {
  setAddingTagJobId(jobId);
}, []);

const handleCancelAddTag = useCallback(() => {
  setAddingTagJobId(null);
}, []);

const handleSubmitAddTag = useCallback(async (job: PrintJob, tagRaw: string) => {
  // Use parseTagsInput to share the D-02 normalize pipeline with the reconcile
  // path. parseTagsInput returns string[] | undefined; we take the first token
  // (commas in input are interpreted as separators — by design, the user can
  // technically paste "a, b" and we add "a"; the trailing token is silently
  // dropped which matches D-02 cap-at-10 semantics for the bulk case).
  const parsed = parseTagsInput(tagRaw);
  const newTag = parsed?.[0];
  if (!newTag) {
    setAddingTagJobId(null);
    return;
  }
  const existing = job.tags ?? [];
  // Already present → no-op (preserve dedupe; D-02). Close the input.
  if (existing.includes(newTag)) {
    setAddingTagJobId(null);
    return;
  }
  // D-02 cap: if already at 10, do NOT add — close the input silently. The `+`
  // affordance is hidden when tags.length === 10 so this branch is defensive only.
  if (existing.length >= 10) {
    setAddingTagJobId(null);
    return;
  }
  const merged = [...existing, newTag];
  await db.jobs.put({ ...job, tags: merged, updatedAt: new Date() });
  setAddingTagJobId(null);
}, []);

// Chip ✕ removal
const handleRemoveTag = useCallback(async (job: PrintJob, tag: string) => {
  const existing = job.tags ?? [];
  if (!existing.includes(tag)) return;  // defensive — race against a stale render
  const next = existing.filter(t => t !== tag);
  // When the filter produces an empty list, persist `undefined` (NOT `[]`) so
  // the "no tags ever set" semantic per D-02 line 43 is preserved.
  const nextTags = next.length > 0 ? next : undefined;
  await db.jobs.put({ ...job, tags: nextTags, updatedAt: new Date() });
}, []);
```
