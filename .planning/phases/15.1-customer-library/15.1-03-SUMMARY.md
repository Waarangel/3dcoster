# Phase 15.1 Plan 03: CSV Bulk Import Summary

CSV bulk import for Customer records is live. Users with existing customer lists (Stripe / Etsy / Shopify exports, hand-maintained spreadsheets) can hydrate the Customers tab in one shot. The pipeline is `Customers tab → Import CSV button → CustomerCsvImportModal (Upload → Preview) → buildCustomersForImport → onBulkImportCustomers → db.customers.bulkPut`. Email-matched duplicates are detected case-insensitively and handled by a single global Skip/Update radio per D-10. The Update path uses merge semantics (D-11) — empty cells in the CSV preserve existing library values, so re-importing a partial export from Stripe will NOT wipe manually-typed notes/address on existing records. Emails are normalized to lowercase on write throughout (UI-SPEC discretion #8) so the parser, the picker, and the de-dup map all share the same key shape.

## Parser Public API (src/utils/customerCsv.ts)

```typescript
export interface ParsedCustomerRow {
  rowNumber: number;                  // 1-indexed; header is row 1, data starts at row 2
  data: Record<string, string>;       // raw header-keyed row (headers already lowercased)
  customer: Partial<Customer> | null; // null when row is invalid (will not be imported)
  errors: string[];                   // ['Name or Email required'] | ['Email format invalid'] | []
  warnings: string[];
  isDuplicate: boolean;               // email matches an existing library record
  existingCustomerId?: string;        // set iff isDuplicate
}

export interface CustomerCsvParseResult {
  rows: ParsedCustomerRow[];
  globalErrors: string[];             // ['CSV file is empty'] | PapaParse error messages
}

export function parseCustomerCsv(
  csvString: string,
  existingCustomers: Customer[],
): CustomerCsvParseResult;

export function buildCustomersForImport(
  rows: ParsedCustomerRow[],
  existingById: Map<string, Customer>,  // id → Customer (built by caller from existingCustomers)
  selected: Set<number>,                // set of rowNumber values to import
  duplicateMode: 'skip' | 'overwrite',
): Customer[];
```

## Email Lowercasing on Write — Confirmed

`validateCustomerRow` lowercases the email via `customer.email = email.toLowerCase();` at the single point where the field is written to the customer object. This means:

- A CSV row with `ALICE@EXAMPLE.COM` becomes `alice@example.com` in `row.customer.email` (verified by Test 4).
- `checkCustomerDuplicates` keys the existing-customer map by `(c.email || '').trim().toLowerCase()` and looks up by `(row.customer.email || '').toLowerCase()` — Test 9 verifies case-insensitive dedup against an existing `Alice@Example.com`.
- `buildCustomersForImport` writes the already-lowercased value via spread on insert and via `if (inc.email) merged.email = inc.email;` on merge — no opportunity to re-introduce mixed case downstream.

This is the same dedup-key shape used by `useCustomers().customersByEmail` from Plan 01 (`(c.email || '').trim().toLowerCase()`), so the picker (Plan 04) and the importer share one source of truth.

## Note for Plan 04 (combobox picker)

`customersByEmail` from `useCustomers()` is the same Map shape used by this CSV importer's dedup logic. The dedup key is `(c.email || '').trim().toLowerCase()` everywhere — parser, builder, hook map, and (per CONTEXT §D-07) the Record Sale auto-link path. Plan 04 can rely on this invariant: any customer record reachable via `customersByEmail.get(email.trim().toLowerCase())` will match a CSV-imported row's `existingCustomerId` lookup byte-for-byte.
