## Customer record + last-used

### Q1: Customer Dexie record shape

| Option | Description | Selected |
|--------|-------------|----------|
| Extend JobCustomer + id/createdAt | New `interface Customer extends JobCustomer { id; createdAt; lastUsedAt? }`. Same 5 fields → zero field mapping into Sale.customer snapshot. | ✓ |
| Define new Customer separate from JobCustomer | Flat interface duplicating fields; forces field mapping forever. | |
| Reuse JobCustomer directly (just add id) | Pollutes the snapshot; risks devs treating `id` as FK. | |

**User's choice:** Extend JobCustomer + id/createdAt
**Notes:** D-01. Zero-mapping path keeps the by-value snapshot rule clean.

### Q2: `lastUsedAt` semantics

| Option | Description | Selected |
|--------|-------------|----------|
| Stored, updated on pick | Written only when picked in Record Sale; O(1) sort. | ✓ |
| Computed from sales table | O(sales) per row render; fuzzy email-match in by-value world. | |
| Stored, updated on pick OR edit | "Last used" drifts to "last touched" — confusing for sort. | |

**User's choice:** Stored, updated on pick
**Notes:** D-03. Edits explicitly do NOT bump the field.

### Q3: Email constraint on the customers store

| Option | Description | Selected |
|--------|-------------|----------|
| Soft dedup (non-unique index) | Indexed for fast lookup; dedup logic in importer + Record Sale 'Add new'. | ✓ |
| Unique constraint on email (when present) | Dexie ConstraintError on dup; blocks couples-sharing-email case. | |
| No email index at all | Walks the whole table for dedup; picker typeahead suffers. | |

**User's choice:** Soft dedup (non-unique index)
**Notes:** D-02. Schema string `'id, name, email, lastUsedAt'`.

### Q4: Delete effect on existing sales' snapshot data

| Option | Description | Selected |
|--------|-------------|----------|
| Nothing — sale snapshots untouched | Locked by ROADMAP success criterion #4. Pure library op. | ✓ |
| Soft-delete (mark inactive, hide from picker) | Adds archive concept; scope creep; thin use case. | |

**User's choice:** Nothing — sale snapshots untouched
**Notes:** D-01/D-14. The by-value architecture already guarantees safety.

## Picker UX in Record Sale

### Q1: Picker style

| Option | Description | Selected |
|--------|-------------|----------|
| Combobox with typeahead | Text input + filtered dropdown; matches ROADMAP "combobox" literal. | ✓ |
| Plain `<select>` dropdown | Doesn't scale past ~50; no email visibility. | |
| Modal picker | 2 clicks, breaks single-modal Record Sale flow. | |

**User's choice:** Combobox with typeahead
**Notes:** D-04. Match on Name OR Email substring (case-insensitive). No new deps.

### Q2: On-pick behavior

| Option | Description | Selected |
|--------|-------------|----------|
| Fill all 4 fields, leave editable | Locked by ROADMAP success criterion #3. | ✓ |
| Fill + lock fields | Contradicts ROADMAP. | |
| Fill + divergence warning on submit | Friction every legitimate per-sale tweak. | |

**User's choice:** Fill all 4 fields, leave editable
**Notes:** D-05. Library not auto-updated from per-sale edits.

### Q3: Auto-save typed values to library on submit

| Option | Description | Selected |
|--------|-------------|----------|
| Auto-save to library on submit | Matches ROADMAP "inline saves to the library on submit"; typeahead = typo prevention. | ✓ |
| Explicit "Save to library" checkbox | Friction every sale; default-checked converges to recommended. | |
| Only save when user clicks "Add new" button | Extra click; doesn't match "inline" language. | |

**User's choice:** Auto-save to library on submit
**Notes:** D-06. Only when Name OR Email non-empty.

### Q4: Typed email matches an existing customer

| Option | Description | Selected |
|--------|-------------|----------|
| Silently link to existing customer | Bump lastUsedAt, no dup, no library overwrite. | ✓ |
| Silently link AND update library record | Surprising; hard to undo legitimate one-off overrides. | |
| Warn user before deciding | Modal in sale flow = friction. | |

**User's choice:** Silently link to existing customer
**Notes:** D-07. Match = `email.trim().toLowerCase()`.

## CSV import + conflict UX

### Q1: Build a new modal or reuse CsvImportModal

| Option | Description | Selected |
|--------|-------------|----------|
| New CustomerCsvImportModal | Sibling of CsvImportModal; same Upload→Preview shell; customer-specific parsing. | ✓ |
| Genericize CsvImportModal | Refactor risk to shipped asset import; "generic enough for 2" trap. | |
| Extract shared dropzone primitive | Shared piece is small; doesn't pay back the new primitive. | |

**User's choice:** New CustomerCsvImportModal
**Notes:** D-08. Parser in new `src/utils/customerCsv.ts`.

### Q2: Required CSV columns

| Option | Description | Selected |
|--------|-------------|----------|
| Name OR Email required, others optional | Forgiving; prevents empty-shell records. | ✓ |
| Name required, email optional | Kills email-only Stripe import path. | |
| Email required, others optional | Kills cash-buyer / in-person workflow. | |

**User's choice:** Name OR Email required, others optional
**Notes:** D-09. All 5 columns accepted; headers case-insensitive; order doesn't matter.

### Q3: Email-match conflict resolution

| Option | Description | Selected |
|--------|-------------|----------|
| Global toggle: Skip / Update duplicates | Mirrors existing `duplicateMode` pattern; one decision per import. | ✓ |
| Per-row choice in preview | Tedious for 50+ conflicts; "Create as new" breaks dedup intent. | |
| Always skip duplicates (no toggle) | Contradicts ROADMAP success criterion #2. | |

**User's choice:** Global toggle: Skip / Update duplicates
**Notes:** D-10. Default = Skip.

### Q4: What "Update" overwrites

| Option | Description | Selected |
|--------|-------------|----------|
| Merge: overwrite only non-empty incoming fields | Re-importing partial CSV doesn't nuke manually-typed data. | ✓ |
| Replace: overwrite all fields (incl. blanks) | Re-importing partial export wipes data — nasty surprise. | |
| Only fill blanks | Too conservative; defies "update = replace" expectation. | |

**User's choice:** Merge: overwrite only non-empty incoming fields
**Notes:** D-11. Imports are additive, not destructive.

## Customers tab UI + delete UX

### Q1: Tab layout pattern

| Option | Description | Selected |
|--------|-------------|----------|
| Mirror AssetLibrary | Virtualized react-window list, search + actions row, EmptyState. | ✓ |
| Single-column dense list (no virtualization) | Contradicts ROADMAP "virtualized list" criterion. | |
| Sortable table view | Net-new pattern for the app; harder in virtualized + responsive. | |

**User's choice:** Mirror AssetLibrary
**Notes:** D-12. Perf budget already paid by Phase 11.

### Q2: Edit pattern

| Option | Description | Selected |
|--------|-------------|----------|
| Modal editor (reused for Create + Edit) | Multi-line Address + Notes don't squeeze into virtualized row. | ✓ |
| Inline-in-row (mirror AssetLibrary) | Row-height jumps; awkward textarea in virtualized row. | |
| Modal for create, inline for edit | Two patterns to maintain. | |

**User's choice:** Modal editor
**Notes:** D-13. Same modal for "Add customer" and per-row "Edit".

### Q3: Delete confirmation

| Option | Description | Selected |
|--------|-------------|----------|
| Simple confirm + sale-reference count | Defuses "will I lose history?" panic; one-shot scan acceptable. | ✓ |
| Plain confirm, no count | Misses the reassurance. | |
| Modal with "View sales" link | Scope creep; user can navigate to Jobs tab. | |

**User's choice:** Simple confirm + sale-reference count
**Notes:** D-14. Copy: "Delete {name}? They appear in {N} past sales — those sales will keep the buyer details on record (this only removes them from your library)."

### Q4: Search input scope

| Option | Description | Selected |
|--------|-------------|----------|
| Name + Email + Company | Matches picker's filter scope; same mental model. | ✓ |
| All 5 fields (incl. Address + Notes) | Noisy false-positives ("st" matches every "street"). | |
| Name + Email only | Excludes "the Acme guy" lookup pattern. | |

**User's choice:** Name + Email + Company
**Notes:** D-15. Case-insensitive substring match.

- Test coverage strategy (CSV merge unit test + by-value snapshot audit test)
