## Fix Details — Iteration 1 (Warnings)

### WR-01: Enter on no-match dismisses customer picker

**File:** `src/components/JobsManager.tsx:579-595`
**Commit:** `e9e9a5e`

The prior code had a comment saying "let Enter submit the form (existing behavior)" but the Record Sale modal is a `<div>`, not a `<form>` — Enter was silently swallowed. The new handler:

- Enter with a valid active option → pick that customer (unchanged).
- Enter with the dropdown open AND a query string AND no match → close
  the dropdown so the user has a clear next step (fill the fields below).
- Enter otherwise (closed dropdown, empty query) → no-op (unchanged).

Also added `customerPickerQuery` to the `useCallback` dependency array so
the new branch reads a fresh value.

### WR-02: Stream sales count in delete-confirm dialog

**File:** `src/components/CustomerLibrary.tsx:180-200`
**Commit:** `454a000`

Replaced `(await db.sales.toArray()).filter(...).length` with
`await db.sales.filter(...).count()`. The store still has no email index
on sales, so the walk is still O(sales), but Dexie streams the iteration
and `.count()` doesn't allocate the array — the JS-heap footprint drops
to a single cursor regardless of dataset size. Performance is listed as
out of scope for this phase, but this is a correctness-adjacent fix
(mobile devices with thousands of sales could lock the UI thread for
seconds during a delete confirm).

### WR-03: Freeze customers array at hook boundary

**File:** `src/hooks/useDatabase.ts:552-575`
**Commit:** `9428874`

Added `customersFrozen = useMemo(() => Object.freeze(customers ?? []))`
and returned the frozen array from the hook. This is a defensive
footgun guard against future consumers accidentally calling
`customers.sort()` or similar in-place mutations on the Dexie liveQuery
cache.

Kept the public type as `Customer[]` (not `readonly Customer[]`) to
avoid rippling a `readonly` type-change through every prop signature.
The runtime freeze still throws on mutation in strict mode; the
compile-time guard is the bit traded away for a much smaller diff.

### WR-04: ArrowDown no-op when picker has zero matches

**File:** `src/components/JobsManager.tsx:561-572`
**Commit:** `b917ffd`

Added an early return at the top of the ArrowDown branch when
`visibleCustomers.length === 0`. Previously the handler unconditionally
opened the dropdown and set active index to 0, surfacing the empty-state
row with an "active" selection that pointed at nothing. Now arrow keys
have no visible effect when there's nothing to navigate; combined with
WR-01, the picker degrades gracefully when no matches exist.

### WR-05: Single source of truth for lastUsedAt bumps

**File:** `src/components/JobsManager.tsx:548-572, 649-664`
**Commit:** `dc7219d`

Removed `await bumpLastUsed(c.id)` from `handlePickCustomer` and made
the callback non-async. The bump now fires exclusively from the
`handleRecordSale` silent-link path at sale-commit time, which is
where the D-07 "linked by email" semantic actually applies.

Two bugs fixed by this consolidation:

1. **Picked-then-cancelled corrupts `lastUsedAt`:** Picking customer
   A and then closing the sale form without saving previously
   advanced A's `lastUsedAt` to "now" even though A was never used
   in a recorded sale. Now: no bump unless the sale is committed.
2. **Picked-then-edited-email double-bumps:** Picking A, then editing
   the email field to B's email and submitting previously bumped
   BOTH A (at pick) and B (at commit via silent-link). Now only B is
   bumped, which is the intended D-07 semantic.

**Verified:** D-05 (Notes preservation) still holds — `setSaleCustomerNotes`
is NOT called by the new `handlePickCustomer`. CL-05 (by-value snapshot)
still holds — `byValueSnapshot.test.ts` passes (3/3).

### WR-06: CSV size cap + binary-file detection

**Files:** `src/components/CustomerCsvImportModal.tsx:68-92`,
`src/utils/customerCsv.ts:53-83`
**Commit:** `b3de9c8`

Two related hardenings:

1. **Modal-level size cap (`MAX_CSV_BYTES = 5 * 1024 * 1024`):**
   `processFile` now rejects files > 5 MB before reading them into
   memory.
2. **Parser-level header validity check:** `parseCustomerCsv` now
   rejects the file if none of the five expected headers (`name`,
   `email`, `company`, `address`, `notes`) are present — catches
   renamed XLSB/binary files that previously surfaced "CSV file is
   empty."

**Verified:** All 12 `customerCsv.test.ts` cases pass.

## Fix Details — Iteration 2 (INFO findings)

### IN-01: Derive useCustomers isLoading from liveQuery value

**File:** `src/hooks/useDatabase.ts:536-543`
**Commit:** `c19758c`

The previous pattern (`useState(true)` + `useEffect` that flips to false
on first `db.customers.count()` resolve) matched the rest of the file's
entity hooks but had a subtle bug: if Dexie re-emits `undefined` mid-session
(e.g. user wipes IndexedDB via DevTools), consumers briefly see
`customers: []` while `isLoading` still reads `false`.

Replaced with `const isLoading = customers === undefined;` — a direct
derivation that mirrors Dexie's own emission semantics. The other entity
hooks (`useAssets`, `usePrinterInstances`, etc.) were intentionally left
untouched per IN-01 scope ("flag for awareness; pre-existing pattern").

### IN-02: SKIPPED — formatRelativeDate locale

**File:** `src/utils/formatRelativeDate.ts:4`
**Status:** skipped — premature i18n

The hardcoded `'en'` locale in `new Intl.RelativeTimeFormat('en', ...)`
is genuinely English-only, but the rest of the app is also English-only:
no `<html lang>` switcher, no copy table, no `react-intl` / `i18next`
integration, no other Intl formatters that take a locale, and i18n is
not on the v1.1 roadmap.

The reviewer flagged this as INFO ("issue is informational"), not as a
bug. Adding `navigator.language` here would create a single
locale-aware formatter inside an otherwise locale-agnostic codebase —
that's a tax on consistency for no current user benefit and a partial-
i18n surface that would have to be untangled when real i18n lands.

When the project picks up i18n properly, this site becomes a one-line
change (accept a `locale` prop or read from a shared LocaleContext) at
the same time as the rest of the i18n migration.

### IN-03: Drop misleading `*` on Name/Email labels

**File:** `src/components/CustomerEditModal.tsx:131-144`
**Commit:** `799c3a4`

The modal previously rendered `Name *` and `Email *` labels, suggesting
both fields were required. The actual validation (line 71) is
`if (!name.trim() && !email.trim())` — "Name OR Email", neither is
individually required. The helper text on line 122 ("Provide at least
one of Name or Email.") already states the rule correctly.

Dropped the `*` from both labels so the visual matches the rule. The
helper text remains as the single source of truth. Submit-button
disabled state and error message are unchanged.

### IN-04: Extract PICKER_VISIBLE_LIMIT constant

**File:** `src/components/JobsManager.tsx:362, 548, 934-936`
**Commit:** `46af834`

The literal `8` was hardcoded in three places:
- `.slice(0, 8)` for the visible-row cap (line 542 pre-fix)
- `> 8` for the overflow-footer threshold (line 928 pre-fix)
- "Showing first 8 of M matches" copy (line 930 pre-fix)

If a future change bumped one without the others, the slice cap and
the footer threshold would silently drift apart. Extracted to a
module-scope `const PICKER_VISIBLE_LIMIT = 8;` (defined above the
component) and threaded through all three sites. Pure cosmetic
refactor — no behavior change.

### IN-05: Memoize RowItem in CSV importer preview

**File:** `src/components/CustomerCsvImportModal.tsx:1, 421-426, 437-510`
**Commit:** `00ce971`

A 1000-row CSV import previously re-rendered every `RowItem` on every
toggle because the parent passed `onToggle={() => onToggleRow(row.rowNumber)}`
— a fresh arrow per render that busted React's referential-equality
fast path.

Three coordinated changes:

1. **Signature change:** `onToggle: (rowNumber: number) => void` (was
   zero-arg `() => void`).
2. **Parent now passes stable callback:** `<RowItem onToggle={onToggleRow}>` —
   `onToggleRow` is already memoized via `useCallback` (line 126), so its
   reference is stable across parent re-renders.
3. **RowItem wrapped in `React.memo`:** the local `handleChange` is built
   with `useCallback([onToggle, row.rowNumber])` so it only rebuilds
   when the row's `rowNumber` changes (essentially never) or the parent
   callback changes (essentially never).

Result: toggling one row now re-renders only that row, not all 1000.
Aligns with the existing project pattern of memoizing list rows.

### IN-06: Remove unused customerPickerInputRef

**File:** `src/components/JobsManager.tsx:1, 384-394, 881`
**Commit:** `c0854e0`

`customerPickerInputRef` was declared and wired to
`<Input ref={customerPickerInputRef}>` (line 881 pre-fix) but never
`.focus()`'d or otherwise read — pure dead code. TypeScript's
`noUnusedLocals` couldn't catch this because the ref WAS technically
used (passed as a prop), even though it produced no behavior.

Three coordinated removals:
1. The `customerPickerInputRef` declaration.
2. The `ref={customerPickerInputRef}` prop on the picker `<Input>`.
3. The now-unused `useRef` import from 'react' (it was the only
   `useRef` usage in the file).

Removal chosen over autofocus-on-modal-open (the other option per
IN-06) because autofocusing the picker would force the user into the
"find existing customer" field first on every Record Sale modal — a
UX decision that belongs in design, not a cleanup pass. A comment-block
was left in place documenting how to restore the ref if a future spec
calls for autofocus.
