# Phase 22.1: Code Review Report

**Reviewed:** 2026-05-28
**Depth:** standard

## Summary

Phase 22.1 closes PERF-08 (widen JobsManager break-even numerator), DATA-07
(Path B reconcile of `fixedCostsAtSave`), WR-01 (drop dead `userProfile` prop),
and WR-02 (stabilize hydration dep array). The schema-extension safety, type
narrowing, and the standalone reconcile helper's test coverage are all clean.

However, the round-trip formula identity that PERF-08 is meant to establish
breaks in two production paths:

1. **CR-01 (BLOCKER) — `db.printers.toArray()` returns an empty table.**
   `reconcileFixedCostsAtSave` is called with `printers=[]` because nothing
   in the codebase ever writes to `db.printers`. The real printer configs
   live in `db.materials` filtered by `category === 'printer'` (see
   `usePrinters`). Result: for every legacy job, `printer` lookups inside
   the reconciler resolve to `undefined`, so `nozzleWear` is always 0 and
   `purchasePrice` falls back to `inst.actualPurchasePrice ?? 0`. Path B's
   "faithful depreciation + nozzleWear reconstruction" silently degrades to
   "depreciation when actualPurchasePrice is set, otherwise zero; nozzleWear
   always zero." Test coverage in `backfill.test.ts` passes only because it
   manufactures a `PrinterConfig` fixture and passes it explicitly — the
   production call site does not.

2. **CR-02 (BLOCKER) — `computeBreakEvenInfo` ignores `modelCostPerUnit`.**
   The Calculator's `fixedCosts` memo zeroes out `modelCost` when
   `modelCostPerUnit === true` (per-unit licensing — model cost is amortized
   into per-unit cost, not into fixed recovery). The JobsManager pill always
   adds `job.modelCost` to the numerator. A job with `modelCost=100,
   modelCostPerUnit=true` will show an inflated `breakEvenCopies` on the pill
   that is $100/profitPerUnit higher than the Calculator widget computes for
   the same job. The PERF-08 round-trip claim is false in this path.

The remaining findings are robustness / clarity concerns. Detail below.

## Critical Issues

### CR-01: Path B reconcile reads from an empty table (`db.printers` is never written)

**File:** `src/hooks/useDatabase.ts:525`
**Severity:** BLOCKER

**Issue:**
The Phase 22.1 fixed-costs reconcile uses `db.printers.toArray()` as one of
its inputs:

```ts
const [printerInstances, printers, materials] = await Promise.all([
  db.printerInstances.toArray(),
  db.printers.toArray(),     // ← always returns []
  db.materials.toArray(),
]);
```

`db.printers` is declared in the Dexie schema (`database.ts:14, 31, 37, ...`)
but **no code path in the codebase ever writes to it**. `grep -rn "db\.printers\." src/`
returns exactly one hit — this read site. The actual `PrinterConfig` data lives
in `db.materials` under `category === 'printer'` (see `useAssets` at
`useDatabase.ts:30-133` and `usePrinters` at `:156-205` which calls
`assetToPrinterConfig`).

Downstream effect inside `reconcileFixedCostsAtSave`
(`backfill.ts:520-541`):

```ts
const printer = printerById.get(inst.printerConfigId);  // ← always undefined
...
const purchasePrice = inst.actualPurchasePrice ?? printer?.purchasePrice ?? 0;
//                                                  ^ skipped
let nozzleWear = 0;
if (printer) {                                          // ← branch never entered
  ...
}
```

For every legacy job, in production:
- `nozzleWear` is always 0.
- `depreciation` works only when the instance has `actualPurchasePrice` set.
  When the user has not explicitly set it (and `PrinterInstance.actualPurchasePrice`
  is `optional`), depreciation also collapses to 0.

This defeats the entire Path B goal — the snapshot becomes "zeros for
nozzleWear, sometimes-zeros for depreciation," which is not "faithful
reconstruction." Worse, the failure is silent: `console.warn` only fires for
the missing-instance branch, not for the missing-printer-config branch.

The test suite (`backfill.test.ts:666-692`) does not catch this because
it passes a synthesized `PrinterConfig` directly to the helper — the missing
piece is the upstream call site, not the helper.

**Fix:**
Use the same adapter the rest of the app uses. Read printer assets from
`db.materials` and pass the converted configs to the reconciler:

```ts
// in useDatabase.ts useJobs(), the fixedCosts reconcile block:
const [printerInstances, printerAssets, materials] = await Promise.all([
  db.printerInstances.toArray(),
  db.materials.where('category').equals('printer').toArray(),
  db.materials.toArray(),
]);
if (cancelled) return;
const printers = printerAssets
  .map(a => assetToPrinterConfig(a))
  .filter((p): p is PrinterConfig => p !== null);
const updated = reconcileFixedCostsAtSave(jobs, printerInstances, printers, materials);
```

Add an import for `assetToPrinterConfig` (already imported in
`useDatabase.ts:5`) and `PrinterConfig` type.

Recommended supplementary test in `backfill.test.ts`: a regression test that
asserts production wire-up — e.g. an integration test that exercises the
actual `useJobs` reconcile path via fake-indexeddb. At minimum, add a comment
to `reconcileFixedCostsAtSave`'s docstring saying "printers MUST be supplied
from db.materials filtered by category==='printer', not from db.printers."

### CR-02: `computeBreakEvenInfo` does not honor `modelCostPerUnit`

**File:** `src/components/JobsManager.tsx:69-71`
**Severity:** BLOCKER

**Issue:**
The widened numerator in `computeBreakEvenInfo` always includes `job.modelCost`:

```ts
const fixedNumerator = job.modelCost
  + (job.fixedCostsAtSave?.depreciation ?? 0)
  + (job.fixedCostsAtSave?.nozzleWear ?? 0);
```

But the Calculator excludes `modelCost` from fixed costs when
`modelCostPerUnit === true` (`CostCalculator.tsx:449-457`):

```ts
const fixedCosts = useMemo(() => {
  const fixedModelCost = modelCostPerUnit ? 0 : modelCost;  // ← zeroed for per-unit licensing
  return {
    depreciation: costs.printerDepreciation,
    nozzleWear: costs.nozzleWear,
    modelCost: fixedModelCost,
    total: costs.printerDepreciation + costs.nozzleWear + fixedModelCost,
  };
}, [...]);
```

`modelCostPerUnit=true` means the model fee is paid per copy (licensing model
— Etsy author resale, etc.). It is rolled into `costPerUnit` already, NOT into
fixed recovery. The Calculator's break-even therefore correctly excludes it.

The JobsManager pill ignores the flag and double-charges `modelCost` into the
break-even numerator. For a job with `modelCost=100, modelCostPerUnit=true,
profitPerUnit=20`, the Calculator shows break-even in 0 copies (no fixed cost
to recover) while the pill shows 5 copies. This contradicts PERF-08's stated
round-trip identity.

The PERF-08 round-trip test in `JobsManager.test.tsx:796-818` does not catch
this because it never sets `modelCostPerUnit=true`.

**Fix:**
Mirror the Calculator's exclusion in the numerator:

```ts
const fixedModelCost = job.modelCostPerUnit ? 0 : job.modelCost;
const fixedNumerator = fixedModelCost
  + (job.fixedCostsAtSave?.depreciation ?? 0)
  + (job.fixedCostsAtSave?.nozzleWear ?? 0);
```

Add a round-trip case to `JobsManager.test.tsx` with
`modelCost=100, modelCostPerUnit=true` and assert `breakEvenCopies === 0`
(since the only remaining fixed costs are depreciation + nozzleWear from the
snapshot, which the case can zero out via `fixedCostsAtSave: { depreciation: 0,
nozzleWear: 0 }`).

### WR-01: Reconcile flag stuck `true` after cancelled-mid-await unmount

**File:** `src/hooks/useDatabase.ts:516-549`
**Severity:** WARNING

**Issue:**
The `fixedCostsReconcileRan` flag is set to `true` BEFORE the async work
runs. If the component unmounts mid-await (`cancelled = true`), the function
returns early via `if (cancelled) return;` — outside the catch block — and
the flag stays `true`. The reconcile is silently skipped for the rest of the
session, even though it never actually wrote anything.

```ts
fixedCostsReconcileRan = true;     // set first
let cancelled = false;
(async () => {
  try {
    const [...] = await Promise.all([...]);
    if (cancelled) return;         // ← early-return BEFORE catch can reset
    const updated = reconcileFixedCostsAtSave(...);
    if (updated.length > 0) { await db.transaction(...); }
  } catch (err) {
    console.error(...);
    fixedCostsReconcileRan = false;  // catch resets — but only on thrown error
  }
})();
return () => { cancelled = true; };
```

The same pattern exists in `copiesSoldReconcileRan` (line 467-496) and
`tagsNormalizeRan` (564-594). All three share the bug.

A user who navigates between routes fast enough to unmount-then-remount the
JobsManager parent will have `fixedCostsReconcileRan === true` but no
snapshot writes. Legacy jobs remain unreconciled until the next page reload.

**Fix:**
Set the flag AFTER the work completes (success or skip), and reset on
early-return cancellation:

```ts
useEffect(() => {
  if (fixedCostsReconcileRan) return;
  if (jobs === undefined) return;
  let cancelled = false;
  (async () => {
    try {
      const [...] = await Promise.all([...]);
      if (cancelled) return;  // do NOT set the flag if we never wrote
      const updated = reconcileFixedCostsAtSave(...);
      if (updated.length > 0) { await db.transaction(...); }
      fixedCostsReconcileRan = true;  // mark only on full completion
    } catch (err) {
      console.error('fixedCosts reconcile failed:', err);
      // flag stays false — next mount retries
    }
  })();
  return () => { cancelled = true; };
}, [jobs === undefined]);
```

This change should be applied symmetrically to the other two reconciles
(`copiesSoldReconcileRan`, `tagsNormalizeRan`) since the bug is the same.

### WR-02: Hydration dep array narrowing creates a latent stale-form bug

**File:** `src/components/RecordSaleModal.tsx:113-159`
**Severity:** WARNING

**Issue:**
The hydration `useEffect` dep array is narrowed to
`[editingSale?.id, convertingFromQuote?.id]` to prevent the WR-02 stale-closure
re-emission. However, the comment claims `Modal.tsx:67 unmounts children on
close, so each open is a fresh mount` — that is true ONLY when `isOpen`
toggles between true ↔ false. When `isOpen` STAYS true and the parent passes
a new `job` prop, the modal does NOT unmount.

JobsManager passes `selectedJob` as the `job` prop. `handleOpenSaleForm`
(line 1136-1143) does:

```ts
setSelectedJobId(job.id);
setEditingSale(null);
setConvertingFromQuote(null);
setShowSaleForm(true);  // already true — no toggle
```

If the modal is already open in create mode and the user (via a future code
path; today the modal is full-screen, so this is latent) triggers
`handleOpenSaleForm` for a different job, the modal stays mounted with a new
`job.id` and `job.sellingPrice`, but `[undefined, undefined]` does not change
— hydration does not re-fire — `salePrice` keeps the OLD job's selling price.

The same applies when switching from `editingSale: null` to `editingSale: null`
across different jobs (e.g., recording back-to-back sales on two jobs).

This is reachable today only via test fixtures (see the new WR-02 test in
`RecordSaleModal.test.tsx:471-515`); the production UI today does not expose
a way to switch jobs while the modal is open. But the contract is fragile:
a future affordance ("Next sale" → switches job without close) would silently
ship a price-prefill bug.

**Fix (low-cost defensive fix):**
Add `job.id` to the dep array so a job-switch re-hydrates create-mode defaults:

```ts
}, [editingSale?.id, convertingFromQuote?.id, job.id]);
```

This still avoids the WR-02 re-emission concern (job.id is the stable
identity, not the mutable sellingPrice).

Alternatively, document the latent issue and add a guard in JobsManager
that calls `setShowSaleForm(false)` before re-opening on a different job. The
dep-array fix is one line; the architectural guard is more invasive.

The eslint-disable comment is fine in principle but should mention this edge
case so the next reader doesn't extend the deps casually.

### WR-03: `if (cancelled) return;` skips write but `if (updated.length === 0)` is silent

**File:** `src/hooks/useDatabase.ts:528-538`
**Severity:** WARNING

**Issue:**
When `reconcileFixedCostsAtSave` returns an empty array (idempotent — every
job already has `fixedCostsAtSave`), the write branch is skipped:

```ts
const updated = reconcileFixedCostsAtSave(jobs, printerInstances, printers, materials);
if (updated.length > 0) {
  await db.transaction('rw', db.jobs, async () => {
    for (const updatedJob of updated) {
      await db.jobs.put({ ...updatedJob, updatedAt: new Date() });
    }
  });
}
```

This is correct. However, when CR-01 is fixed and the reconcile actually
runs successfully, every legacy job's `updatedAt` is bumped to `new Date()`
— even though the only real change is the addition of a snapshot field.

That side effect:
1. Re-sorts the JobsManager list by `updatedAt` (if any view sorts by it).
2. Cascades through any UI that surfaces "last modified" timestamps.
3. Hurts user trust ("why does every job say it was edited today?").

The `copiesSoldReconcileRan` and `tagsNormalizeRan` paths do the same. They
are all silent UX regressions on the first reload after the migration ships.

**Fix:**
Preserve `updatedAt` in the reconcile write — the field hasn't logically
changed:

```ts
for (const updatedJob of updated) {
  await db.jobs.put(updatedJob);  // updatedAt was NOT in the helper output, so it stays as the row's original
}
```

The helper's `out.push({ ...job, fixedCostsAtSave: {...} })` already spreads
the existing `updatedAt`, so dropping the override here is correct. Same fix
applies to the other two reconciles (they DO need to bump `updatedAt` for
content-changing reconciles like tag normalization — but the snapshot-only
case here doesn't).

### WR-04: `searchedJobs` search misses snapshot-only fields silently

**File:** `src/components/JobsManager.tsx:1026-1039`
**Severity:** WARNING

**Issue:**
The search filter inspects `job.name`, `job.tags`, and the per-job sales'
`customer.{name,email,company}`. It does NOT inspect `fixedCostsAtSave`,
which is correct semantically.

However, the filter relies on `salesByJob.get(job.id) ?? []` returning a
non-empty array per Sale, but `s.customer?.name || ''` will fall back to
empty string when only `customerName` (legacy field) is set. The
RecordSaleModal hydration block at line 119 correctly falls back to
`editingSale.customer?.name ?? editingSale.customerName ?? ''`, but the
search filter does not — pre-Phase-14 sales with only `customerName` are
not searchable.

This is not a Phase 22.1 regression (it pre-dates this phase) — but the
phase context calls for "every fact, risk, or data point" to be surfaced
even when adjacent. Flagging here because the same legacy-data-shape concern
that motivates Path B reconcile also motivates pre-Phase-14 customerName
handling.

**Fix:**
```ts
return jobSales.some(s => {
  const name = (s.customer?.name || s.customerName || '').toLowerCase();
  return name.includes(q)
    || (s.customer?.email || '').toLowerCase().includes(q)
    || (s.customer?.company || '').toLowerCase().includes(q);
});
```

Optional — not blocking — but adjacent to the legacy-data reconcile pattern
the phase enshrines.

### IN-01: Reconcile helper docstring says `console.warn` fires "with the job's name + id" — confirm production callers respect the warn

**File:** `src/db/backfill.ts:482-491`
**Severity:** INFO

**Issue:**
The docstring promises:
> ...a `console.warn` carrying the job id + name is emitted.

This is true at the helper level. But the helper is called inside
`useDatabase.ts`'s reconcile useEffect with a `try/catch` that swallows
nothing (it logs `console.error` on thrown errors only). The warn DOES

However, if a user has 50 legacy orphan jobs (e.g., they wiped their
printers list while keeping print jobs), they will get 50 console.warn

unguarded — there is no `console.warn` rate-limit.

**Fix (optional):**
Aggregate the warn at the call site instead of per-job in the helper:

```ts
const updated = reconcileFixedCostsAtSave(...);
const orphans = updated.filter(j => j.fixedCostsAtSave?.depreciation === 0
                                 && j.fixedCostsAtSave?.nozzleWear === 0);
if (orphans.length > 0) {
  console.warn(`[fixedCosts reconcile] ${orphans.length} orphan jobs snapshotted with zeros:`,
               orphans.map(j => j.id));
}
```

…and drop the per-job warn from the helper. This is a quality-of-life nit,
not a defect.

### IN-02: `Promise.all` reads three Dexie tables — consider transaction scope for consistency snapshot

**File:** `src/hooks/useDatabase.ts:523-527`
**Severity:** INFO

**Issue:**
The three reads (`printerInstances`, `printers`, `materials`) are NOT in a
shared Dexie transaction. If a user is concurrently editing a printer's
nozzleCost in another component during the reconcile, the snapshot could be
internally inconsistent (one read sees the old value, another sees the new).

In practice this is extremely unlikely (the reconcile runs once at page
load, before the user can touch settings), but the convention elsewhere in
the file is `db.transaction('rw', ..., async () => {})` for any
multi-table read+write — see `useSales.addSale` at line 638-651.

**Fix (optional):**
Wrap the read pass in a `db.transaction('r', ...)`:

```ts
const [printerInstances, printerAssets, materials] = await db.transaction(
  'r', db.printerInstances, db.materials, async () => Promise.all([
    db.printerInstances.toArray(),
    db.materials.where('category').equals('printer').toArray(),
    db.materials.toArray(),
  ])
);
```

(Note: this builds on the CR-01 fix.) The behavioral change is negligible
under today's UX, but it matches the file's prevailing convention.
