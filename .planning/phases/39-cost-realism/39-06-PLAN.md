<objective>
Close the two UAT gaps from Phase 39 test 5 (minor) and test 6 (major): the TOU
band time-window inputs are unusable. Native `<input type="time">` controls are
squeezed into ~80px grid columns so their minute/AM-PM segments and picker glyph
clip to "0 --"/"PM", and Chrome paints the internal clock glyph in light-scheme
colors (near-black) on the dark `bg-slate-700` field. Worse, a native time input
reports `value === ''` until every segment is complete, so the "+ Add band"
button — hard-gated on all four fields being non-empty — never enables and its
error feedback (only set inside the unreachable handler) never shows. No band can
be created, which makes the entire calculator TOU path (test 6) unreachable.

Fix per the debugger's recommended direction: replace the native time inputs with
plain text HH:MM inputs (placeholder "22:00") validated through the already-strict
`parseHHMM`/`upsertBand` path, and replace the silent disabled gate with real
validation feedback. Apply the same swap to the calculator's start-time picker so
the UX is consistent and the dark-glyph problem is fixed there too.

Purpose: Make TOU bands actually configurable and usable — the feature exists in
code but is unreachable through the UI.
Output: Usable, readable, validated HH:MM entry in Settings and the calculator,
plus regression tests that would have caught this failure class.
</objective>

- `useTouTariff(electricity, onElectricityChange)` returns
  `{ flatRate, bands, setFlatRate, upsertBand, removeBand }`
- `upsertBand(band: TouBand): string | null` — returns a user-facing error
  message on rejection (invalid rate/HH:MM, overlap, or >3 bands), or `null` on
  success. It already validates via parseHHMM. It does NOT validate band.name.
- `MAX_TOU_BANDS = 3`

From src/utils/touElectricity.ts:
- `parseHHMM(s: string | undefined): number | null` — strict 24h "HH:MM"
  (zero-padded 2-digit hour, 00-23; minutes 00-59). '9:30' → null, '24:00' → null.
- `resolveWeightedCostPerKwh(...)` — already falls back to the flat rate when
  startTime is missing/malformed, so a partial calculator entry ('2') simply
  prices at the flat rate until it becomes a valid HH:MM. Never throws / NaN.
