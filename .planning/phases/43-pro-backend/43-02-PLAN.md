<objective>
Prepare the app's network boundary and compliance surface for the first backend BEFORE any Pro code calls out: update the data-flow inventory FIRST (Pitfall C-05 discipline), then the CSP, the SPA-fallback rewrite in `vercel.json`, AND the PWA service-worker navigation fallback in `vite.config.ts`, then the Privacy Policy and the Terms-of-Service Pro-billing section.

Purpose: The existing strict CSP (`connect-src 'self' ...`, `script-src 'self'`, `frame-src 'none'`) will silently block Supabase auth/REST calls and Paddle's checkout iframe the moment they are added — with no error beyond a console CSP violation. The current catch-all rewrite (`/(.*) -> /`) will swallow every `/q/[token]` request before the new Vercel function can run. AND — the second, easily-missed SPA-fallback layer — the installed PWA service worker registers scope `/` (`vite.config.ts`), so its navigation fallback can serve a cached SPA shell for a `/q/*` navigation before the request ever reaches Vercel, showing a stale/precached page after a maker unpublishes (Research Open Question 2). All three (CSP, server rewrite, SW denylist) must be fixed before auth (43-03), hosted pages (43-05), and billing (43-06) can function. The GDPR docs carry forward the Phase 42 hard-gate obligations.

Output: An inventory that matches what the code is about to do, a CSP/rewrite that permits exactly the new origins/routes, and live legal text with concrete Pro terms.
</objective>
