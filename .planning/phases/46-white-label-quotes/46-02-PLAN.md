<objective>
Enable Supabase Pro auth on the Tauri desktop build (D-08 scope expansion) so white-label works on desktop too. Today the desktop app is fully gated off Pro: `supabaseClient.ts` returns `null` at module level whenever `__IS_TAURI__` is true, `release.yml` injects no `VITE_SUPABASE_*`, and Tauri's CSP `connect-src` lists no `*.supabase.co`. This plan closes all three gaps and adds the email-OTP code-entry path (`verifyOtp`) to the existing magic-link flow. Session persistence uses the WebView's built-in `localStorage` (RESEARCH A1 — no new Tauri plugin, mirroring the accepted web disposition T-43-09).

Purpose: The white-label PDF (46-04) and Branding UI (46-06) must resolve `isProStatus` on desktop, which is impossible while the desktop Supabase client is null.
Output: A desktop-capable Supabase client, an OTP verify path in `useProAuth`, an OTP code-entry step in `SignInModal`, and the two infrastructure fixes (CSP + CI env).

Decision coverage: D-08 (desktop Pro auth via email OTP code entry; NO custom-protocol deep-link).

Documented scope decision (resolves RESEARCH Open Question 1 / Assumption A5): Desktop gains sign-in + entitlement + white-label PDF ONLY. Hosted-quote PUBLISHING (`ShareQuoteButton`) stays web-only — its `if (__IS_TAURI__) return null` gate is DELIBERATELY left in place this phase. The phase goal is PDF + hosted-page BRANDING, not desktop publishing; a desktop Pro user can still open 3dcoster.com in a browser to publish. Do not remove ShareQuoteButton's gate.

Notes: Spec-less probe fallback SKIPPED (no requirement IDs — visible recorded skip). Schema-push gate N/A (no schema files).
