<objective>
Close gap G-46-4 (per D-09 contextual sign-in) and the CLIENT half of G-46-2
(per D-08 desktop auth).

G-46-4: useProAuth.status is trapped at 'link-sent' with no user-driven exit,
and SignInModal is permanently mounted (App.tsx:363-366), so closing/reopening
cannot reset it. Abandoning via the code-step Cancel leaves status stuck →
reopen shows an EMPTY but DISABLED email field on the code step (the user's exact
screenshot). Close paths are inconsistent: code-step Cancel routes through
resetAndClose (clears local email/code) while X/backdrop/Escape call the raw
onClose (stale email survives) — and none can touch status.

G-46-2 (client half): SignInModal copy promises "a magic link and a one-time
code" unconditionally, but a brand-new user's first email may be a signup
confirmation. Make the copy accurate and decide shouldCreateUser explicitly.
(The PRIMARY G-46-2 fix — the Supabase 'Confirm signup' template — is plan 46-08.)

Purpose: give the sign-in flow an explicit, user-driven way back from
'link-sent' so a typo'd email or an abandoned attempt is always recoverable
in-session, and stop the copy from over-promising a code new users may not get
until the template fix lands.
Output: a resetSignIn() action on useProAuth, one unified SignInModal close
handler, a 'Use a different email' affordance, accurate first-time copy, and
lifecycle tests that actually exercise the status transition the old frozen-mock
tests could not.
</objective>
