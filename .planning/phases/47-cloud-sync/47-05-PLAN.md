<assumption_delta_decision>
The assumption-delta detector fired (`kind: pluralization`) for Phase 47: this phase introduces a SECOND sync transport (cloud) where there was one (file sync — Phase 44), and D-04 makes them coexist.

- **Primary noun now:** the `SyncFile` envelope (transport-agnostic sync payload) plus the shared `syncStamp` `updatedAt` stamps + `syncTombstones` — the merge infrastructure.
- **Decision: `no-change` (promotion already occurred in Phase 44).** Phase 44 designed the merge core transport-agnostic: `computeMerge`/`applyMerge`/`validateSyncFile` operate on the `SyncFile` shape independent of where it came from. Cloud sync is a clean SECOND VARIANT that produces/consumes the same primary `SyncFile` — not a new primary added alongside a still-file-specific one. We are exercising the seam Phase 44 built, not contradicting a singular assumption.
- **Deliberate `add-alongside` (accepted, scoped):** per-transport sync STATE is legitimately plural — file sync tracks `lastSyncedAt` (a folder has no version counter); cloud sync tracks a `version` CAS counter + `lastKnownVersion` (a blob has no folder handle). D-04 explicitly wants "independent channels sharing one merge engine." No single "sync cursor" primary makes sense across a folder and a CAS-versioned blob, so two channel states alongside one shared merge core is correct, not debt.
- **What would force a later promote:** if a THIRD transport appeared, or if server-side querying were ever wanted (foreclosed by zero-knowledge D-05), the channel-state duplication should be generalized behind a transport interface.
- **Invariant test (adopted):** the useCloudSync round-trip test asserts the cloud payload is a byte-identical `SyncFile` that `validateSyncFile` accepts and that deletes route through the same `syncStamp` tombstone path — this goes red the instant a future change forks the cloud payload away from the shared primary.
</assumption_delta_decision>
