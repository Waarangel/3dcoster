## Summary

This is a purely additive, client-only feature. Today a job stores post-processing consumables as `materialsUsed: MaterialUsage[]` and shipping packaging as `packagingMaterials?: MaterialUsage[]`, and both are `{ materialId, quantity }` pointers into the asset library. Cost is **re-derived at calculation time** from live library prices (`calculateCost` for post-processing, `packagingCost` in `useCostDerivedValues` for packaging), then **snapshotted as a single number** (`costPerUnit: trueCost`) when the job is saved. Every downstream consumer I checked (My Jobs, sales profit, sales-report PDF, insights failure-scrap cost, break-even pill, quote PDF line items, hosted quotes) reads `job.costPerUnit` or the quote's by-value snapshot - **none of them walk the material lists.** That makes the feature cheap and safe to land: if the manual lines are added into `calculateCost` / `packagingCost`, `trueCost` and therefore the saved `costPerUnit` include them automatically and every report reconciles with no further changes.

The recommended shape is **two new optional arrays on `PrintJob`** (`manualMaterials?`, `manualPackaging?`) of `{ id, name, cost, libraryPrompted? }`, rather than overloading `MaterialUsage`. `MaterialUsage` is consumed by the stock ledger (`buildJobStockEvents` would mint phantom `jobId__undefined` events), the CSV flattener, and name-resolution paths that all assume an asset id. Separate arrays are structurally invisible to those consumers, need **no Dexie version bump** (non-indexed optional fields are the established pattern; DB is at v13), need **no reconcile helper** (legacy jobs have `undefined` == `[]`, so no derived value changes for any existing record), and ride along inside the existing backup/sync job records untouched (records are opaque `unknown[]` to `validateBackupFile`, written verbatim by `applyMerge`; the cloud blob is the same envelope, so there is no Supabase-side schema).

The real work is in five places the planner must not miss: (1) both `calculateCost` calls in `useCostDerivedValues` (the `costsForTrueCost` bootstrapping pass AND `costs`), (2) the form-state plumbing in `useCostForm` (sessionStorage draft, Edit re-hydrate, clear), (3) the explicit-allowlist `duplicateJob`, (4) the Save Job popup + a new `onAddAsset` prop threaded from `App.tsx`, and (5) the Jobs CSV export columns. The hardest product call is the "added to library" semantics: recommend keeping the by-value manual line on the job (do NOT convert it into a library-linked `MaterialUsage`) so there is no double count and no phantom negative stock.

**Primary recommendation:** Add `ManualCostLine` + two optional `PrintJob` arrays; sum them inside `calculateCost` (post-processing) and `useCostDerivedValues.packagingCost` (shipping/packaging); render them as a "One-off" row type in the existing two lists; show a pre-save `Modal` with a per-row `Select` ("Keep as one-off" default / "Add to library") that calls the existing `addAsset`; flag lines `libraryPrompted` so edits don't re-ask; leave the saved line as a by-value manual line.

### Pattern 1: Cost math lives in `costCalc.ts`, additive and default-neutral
**What:** Add a pure helper and an optional `CalcInput` field; default `undefined` contributes `0`, keeping every existing golden scenario byte-identical (this is exactly how Phase 39 added `maintenanceCostPerHour`).
**Evidence (verbatim):** `costCalc.ts:234` `const materialsCost = input.materialsUsed.reduce((total: number, usage: MaterialUsage) => {` and `costCalc.ts:262` `const perUnitSubtotal = filamentCost + electricityCost + materialsCost + laborCost + perUnitModelCost + maintenanceCost + abrasiveSurcharge;` [VERIFIED: src/utils/costCalc.ts:234,262]
**Example (new code, shape only):**
```typescript
// src/utils/costCalc.ts
export interface ManualCostInput { cost: number }

/** Σ of finite, positive manual costs, each rounded to cents. Undefined/empty -> 0. */
export function calculateManualLinesCost(lines: readonly ManualCostInput[] | undefined): number {
  if (!lines) return 0;
  return lines.reduce((sum, l) => (Number.isFinite(l.cost) && l.cost > 0 ? sum + Math.round(l.cost * 100) / 100 : sum), 0);
}
// in CalcInput:        manualMaterials?: ManualCostInput[];
// in calculateCost():  const materialsCost = <existing reduce> + calculateManualLinesCost(input.manualMaterials);
```
Because `materialsCost` feeds `perUnitSubtotal` -> `failureAdjusted`, a manual post-processing line is multiplied by the failure multiplier exactly like a library material. That is consistent with how library post-processing materials already behave. Manual **packaging** lines are NOT failure-adjusted, also consistent with library packaging (`trueCost = costs.failureAdjusted + totalShippingCost`). [VERIFIED: useCostDerivedValues.ts:309,496-ish `trueCost` derivation read in full]

### Pattern 4: Save Job library prompt (pre-save, in the orchestrator)
Reuse `Modal` (portal, focus trap, Escape/backdrop close, children only mount when open, so per-open state resets for free - see `DeclineQuoteModal` for the chrome and footer convention). [VERIFIED: src/components/ui/Modal.tsx header comment, src/components/DeclineQuoteModal.tsx]
Flow inside `handleSaveJob` (after the three existing validation toasts, before `onSaveJob`/`onUpdateJob`):
1. Build normalized lines (trim name, round cost to cents, drop rows with blank name AND cost 0; if any row has cost > 0 and a blank name -> `toast.error` + abort, matching the existing `toast.error('Please enter a name ...')` style).
2. `promptable = lines.filter(l => !l.libraryPrompted && !existsInLibrary(l.name))` (case-insensitive trimmed name match against `materials`; dedupe by normalized name within the prompt).
3. If `promptable.length === 0` -> save as today. Else open the modal with one row per promptable line: a shared-`Select` ("Keep as one-off" default, "Add to library"); for post-processing rows an additional category `Select` (see Open Question 5); packaging rows are fixed to `packaging`.
4. Confirm -> `await onAddAsset(asset)` for each "Add" row, set `libraryPrompted: true` on every line that was shown, then call `onSaveJob`/`onUpdateJob` with those lines. **Cancel / Escape / backdrop = abort the save** (job not written, form untouched) - label the footer buttons "Cancel" and "Save job" so the semantics are unambiguous.
5. Guard re-entry (`isSaving` state) because the handler is async and the modal confirm is a second async step.

### Anti-Patterns to Avoid
- **Reusing `MaterialUsage` for manual lines** - see Alternatives. Phantom stock events and cost-0 rows.
- **A second cost formula** in the section components or panel. `CostSummaryPanel` already shows `costs.materials` and `packagingCost`; because manual cost is merged into those numbers, itemized rows still sum to the Subtotal (the Phase 39 WR-06 invariant). No panel math changes needed. [VERIFIED: CostSummaryPanel.tsx:70-100]
- **Rounding on every keystroke** into a controlled number input (fights the caret / `1.`). Round at the boundary: in `calculateManualLinesCost` and the save-normalization step. Display 2dp via `toFixed(2)` like the neighbouring rows.
- **Index keys** on the manual list. Use `line.id`.
- **Re-asking on every Edit/Update.** Persist `libraryPrompted`.

## Common Pitfalls

### Pitfall 1: Updating only one of the two `calculateCost` calls
**What goes wrong:** `useCostDerivedValues` computes cost twice: `costsForTrueCost` (bootstrapping pass feeding `trueCostForReducer`) and `costs` (returned to callers). If `manualMaterials` is passed to only `costs`, the panel/saved `costPerUnit` are right but the pricing reducer derives selling price from a *lower* cost basis - margin/price look correct, then drift on the next RECALC.
**Why:** the two calls are deliberately byte-identical except for pricing pass-through fields. [VERIFIED: useCostDerivedValues.ts:323-336 comment, 337, 456]
**Avoid:** pass the new input to BOTH and add it to BOTH `useMemo` dependency arrays. Also add `manualPackaging` to the `packagingCost` memo deps. **Warning sign:** `trueCostForReducer !== trueCost` in a unit test (assert equality with manual lines present).

### Pitfall 2: `nonPricingFormState` memo missing the new slices
**What goes wrong:** the sessionStorage draft effect deps the `nonPricingFormState` object; if the new state isn't both in the object AND in its `useMemo` dep list, manual lines are not persisted (or persist stale) and a page reload loses the user's one-off entries. [VERIFIED: useCostForm.ts nonPricingFormState block + its dep array]
**Avoid:** add to both; test: type a manual line, remount without editingJob, expect it restored.

### Pitfall 3: Edit re-hydrate leaks the previous draft
**What goes wrong:** the existing packaging restore is guarded - `useCostForm.ts:233` `if (editingJob.packagingMaterials !== undefined) setPackagingMaterials(...)` - which means "leave the form alone when the saved job lacks the field". Copying that guard for the new fields would let an unsaved draft's manual lines bleed into the job being edited (and then get saved onto it). [VERIFIED: useCostForm.ts:233]
**Avoid:** set unconditionally: `setManualMaterials(editingJob.manualMaterials ?? [])`, same for packaging (mirrors how `materialsUsed` is restored unconditionally). Test with a legacy job (fields undefined) while a draft exists.

### Pitfall 4: `clearForm` / finishAfterSave not resetting new state
`clearForm` enumerates every setter explicitly; the new slices must be reset there (and `sessionStorage.removeItem` already clears the blob). Cancel-Edit and post-save both route through `clearFormAndPricing`. [VERIFIED: useCostForm.ts clearForm, CostCalculator.tsx clearFormAndPricing]

### Pitfall 5: `duplicateJob` silently drops the lines
See matrix. The duplicate would have a `costPerUnit` that includes manual cost but no manual lines to explain it, and re-saving it after Edit would silently lower the cost. Test: duplicate carries both arrays by value (mutating the copy doesn't affect the source).

### Pitfall 6: Double counting when an item is "also added to the library"
Two distinct hazards:
- **Convert-to-linked** (replacing the manual line with `{ materialId: newAsset.id, quantity: 1 }`): if the manual line isn't removed in the same step the cost counts twice; if it is converted, `buildJobStockEvents` deducts 1 from a brand-new asset with no stock history -> stock goes to `-1`, and the "set stock on hand" UX (`stockByAssetId.size === 0` prompt) and any low-stock logic see a surprising negative.
- **Re-picking later:** user adds the same item from the picker on the next job - no problem, that is the point of adding it.
**Recommendation:** keep the saved line as a by-value manual line; creating the asset is a *library-only* side effect. Cost on the job is unchanged, stock untouched, nothing to double count. Name-dedupe against the existing library so accepting twice (e.g. save fails, user retries) doesn't create duplicate assets. See Open Question 3.

### Pitfall 7: Prompt fires on every Edit / double-prompt after failure
Without `libraryPrompted`, each "Update Job" re-asks about the same lines. Set the flag for every line shown in the modal (accept OR skip). If `onAddAsset` throws mid-way, show `toast.error` and abort the job save (nothing flagged), so a retry re-prompts only what's still un-added (name-dedupe skips what was created).

### Pitfall 8: Blank / invalid rows
Define once, in the pure helper, and test it: math counts only `Number.isFinite(cost) && cost > 0`; save requires a trimmed non-empty name for any costed row (block with toast); fully empty rows are dropped silently; names are bounded (pick a named constant, e.g. `MANUAL_LINE_NAME_MAX_LENGTH`, the repo has no existing max for asset names - AssetLibrary sets no `maxLength`). Do NOT invent a maximum cost - the project rule is no arbitrary numbers; any plausibility warning needs a sourced threshold, so skip it.

### Pitfall 9: Coverage gate on the two files this change touches
`vitest.config.ts:25-29` enforces `lines: 95, functions: 100, branches: 90` on exactly `src/utils/costCalc.ts` and `src/hooks/useCostDerivedValues.ts`, and `npm run build` runs `vitest run --coverage`. Every new function and branch in those two files (empty/undefined lines, non-finite cost, zero cost) needs a test or the **release build fails**. [VERIFIED: vitest.config.ts:25-29, package.json build script]

### Pitfall 10: Source-scan and snapshot tests
Several tests `readFileSync` component source and assert string occurrences (e.g. exactly one `taxRate: tax.ratePercent`, zero `updated[index] =`). `outputEquivalence.test.tsx.snap` is "do not regenerate" - new inputs default to empty, so numbers must stay byte-identical; if that snapshot changes, the change is wrong. [VERIFIED: CostCalculator.test.tsx:113-150,164-186; outputEquivalence.test.tsx header]

### Pitfall 11: Older app build on another synced device
A device still on a pre-47.1 build ignores the new fields; if it edits and re-saves that job via the form, `{ ...editingJob, ...sharedFields }` preserves the unknown manual arrays but `costPerUnit` is recomputed without them -> cost mismatch until that device updates. Web auto-updates; low risk. Mention in the plan's risk notes; no mitigation required (no version gate exists in sync today - `appSchemaVersion` is diagnostics only). [VERIFIED: backupSchema.ts BackupMeta comment "diagnostics only"]

### Pitfall 12: Currency
Manual costs are entered directly in the profile currency and snapshotted under the existing `job.currency` (stamped at save). No FX conversion path is needed or wanted (library prices are converted via `convertToProfile`; manual entries bypass it). The newly created asset must carry `currency: userCurrency` so display-time conversion works later. [VERIFIED: useCostDerivedValues.ts convertToProfile/materialsInProfile; CostCalculator.tsx `currency: userCurrency`]
